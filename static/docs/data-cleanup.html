Trash cleanup and retention

Open the administrator account menu → Settings → Trash cleanup. The master switch and every data type start disabled. Installing this update does not schedule deletion until an administrator enables and saves rules. Existing file Trash and wiki recovery points no longer expire automatically after seven days.

Cleanup permanently removes eligible data. EagleIDE cannot undo it. Keep a private instance backup and choose retention periods appropriate to your classroom before enabling a type. Whole-wiki backups and recovery points have separate rules and may still contain content removed from the current wiki.

Set up cleanup

  1. Review the data types below, select Enabled for the types you want, and set whole days from 1 to 3650. Defaults are suggestions, not enabled policies.
  2. Turn on Enable automatic data cleanup and select Save cleanup rules. Saving another Settings section does not save cleanup rules. Clean now is unavailable while changes are unsaved.
  3. Select Clean now to apply the saved rules immediately. It uses the same ages as automatic cleanup; it does not empty recent Trash or bypass retention. Confirm the permanent deletion prompt.
  4. Inspect Recent cleanup runs and the Permanent deletion log. A background worker keeps the request short. Automatic checks run hourly; after startup/enabling, the first check can occur within about a minute.
  5. To stop further operations, disable the master switch or a type and save. A file operation already started can finish. Any saved policy change stops the current run; the next run uses the new rules.

Settings use revision checks to prevent another tab silently overwriting them. If a save reports that settings changed, use Refresh, confirm discarding the local draft, and review the saved policy. Switching accounts clears the displayed history; cleanup settings and receipts are never written to browser storage.

Protected data and practical limits

Cleanup never deletes a current account, including a disabled account, because it is old or inactive. Active workspace files, current classes, lesson plans, published wiki content, settings, credentials and the cleanup ledger are protected. Account recreation is briefly blocked for that identity while its old owned data is being purged; unrelated accounts can continue working. If an authoritative user store is unreadable, deleted-user cleanup stops rather than assuming everyone was deleted.

Account deletion still performs its existing immediate account/workspace/tool removal; the new rule addresses retained remnants afterward. This is not a universal identity-erasure tool: copies shared into someone else’s workspace, teacher-authored or other shared classroom material, wiki authorship metadata, and content in separately retained backups/recovery points are not removed by the deleted-user rule. Unrecognized loose files are preserved. Review these stores separately for a complete erasure request.

Existing byte/count safety caps remain: server-log size rotation, bounded event lists, limited page revisions/submission history, storage quotas, and runtime/upload protocol expiry. Successful runs, downloads and uploads still release their temporary files normally. Those existing operations and explicit user deletions are not recorded in this cleanup ledger. The new controls govern age-based maintenance of the listed stores; they do not control operating-system logs, service stdout, Cloudflare logs, browser recovery drafts, offsite backups or arbitrary folders.

A sweep is limited to 20,000 recorded operations and a directory scan to 100,000 entries. Large stores continue on a later sweep or another Clean now. JSON/log reads have a 50 MiB safety limit. A partial or stopped run can have completed some eligible deletions; review individual receipts and retry after resolving failed storage access. Symbolic links/junctions and paths outside the registered store are refused. Local administrators must protect runtime directories from unauthorized filesystem changes.

Removing files frees filesystem references; SQLite row cleanup uses secure deletion where supported. This does not guarantee forensic overwriting on SSDs, snapshots or backup media. SQLite catalogs can retain allocated disk space for reuse after row deletion; disruptive compaction is not run against the live service.

Permanent deletion log and deployment

The private cleanup_data/cleanup.sqlite3 stores policy, deletion/observation clocks, run summaries and permanent receipts. Set EAGLEIDE_CLEANUP_DATA_DIR to a persistent private directory if needed. Keep it outside public/static folders and include it in private instance backups. Do not publish it or commit it to Git. New directories/files use restrictive permissions on POSIX; configure Windows ACLs and backup access appropriately.

Each file/directory receipt includes its name, full server path, type, operation, time, outcome and estimated bytes. In-place JSON/SQLite pruning records the containing path/table and record count, without copying deleted record contents. Paths/titles can themselves contain personal information. This metadata is intentionally retained indefinitely, administrator-only, as requested; cleanup never removes the ledger. The log is not a tamper-proof external audit service.

A planned receipt is committed before deletion. If the ledger cannot be written, no further deletion is attempted. Deleted confirms a completed operation, skipped means already absent, and failed records an error type. A crash can leave a planned entry with uncertain outcome; restarted runs are marked interrupted. Check the private filesystem and rerun the saved rules. Do not treat planned or failed as proof of erasure.

The deployment adds no dependency, account/content migration, or extra service. Deploy with your normal graceful application restart after saving work; existing in-memory sign-ins and runner sessions follow the normal restart lifecycle. Keep the cleanup directory when rolling back or replacing the checkout. Reverting to older application code can restore that version’s hardcoded expiry behavior, so review retention before rolling back.
