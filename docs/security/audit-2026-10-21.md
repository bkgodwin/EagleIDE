# EagleIDE Security Analysis — code.mrgodwin.com

**Date:** 2026-10-21
**Codebase audited:** `bkgodwin/EagleIDE` at HEAD `c05bc0e` (merge of PR #188), local clone `~/workspace/projects/EagleIDE`
**Method:** Static, read-only audit of the full codebase (~13,300-line `app.py` plus all feature modules, sandbox workers, and frontend JS), repo-wide grep verification for every absence claim, plus live checks of the public site's response headers and the repository's git history. ## 1. Executive summary

EagleIDE's *application-internal* security engineering is well above the norm for a self-built school project — in places (the external-tools gateway, the Python sandbox, the token/capability designs) it is genuinely rigorous. The serious risks are concentrated in four areas:

1. **The deployment edge does not match the intended topology.** The design assumes "internet exposure only via Cloudflare Tunnel, LAN is trusted." In reality the Werkzeug dev server binds `0.0.0.0`, speaks plaintext HTTP, has no sign-in throttling and no IP allowlist, and trusts proxy headers from *any* private address — so every student device on the school network gets a direct, unthrottled, spoofable shot at the admin login, bypassing all Cloudflare protection. (EAG-SEC-001, 002, 003)
2. **Student personal data is plaintext at rest, and one public claim about it is false.** `users.json` stores every student's name, email, and student ID unencrypted, and the live Wiki Information page's statement that "names and emails [are] encrypted" is not true of the implementation. The Fernet key that does exist protects only the admin password and sits in the same directory as the data. (EAG-SEC-014)
3. **Erasure does not erase.** Account deletion removes the user record and workspace but leaves submissions, grades, notebooks, and keystroke-level development recordings behind — indefinitely, with no retention clock — and in some failure modes reports success (or "user not found") for a half-completed deletion. Teacher deletion orphans an entire class's data, including live public share tokens. (EAG-SEC-025, 026, 029)
4. **Two concrete, exploitable chains exist today:** the cross-class leaderboard API returns every student's email to any signed-in student (EAG-SEC-015), and the HTML runtime serves student-planted `.svg`/`.htm` files script-live on the main origin, enabling teacher session-token theft via a link a teacher would plausibly click during class (EAG-SEC-033).

There are also two "loaded gun" process risks: `assignment_submissions/` is missing from `.gitignore` in a **public** repo (EAG-SEC-020), and publicly checked-in default admin credentials are one bootstrap bypass away from being live (EAG-SEC-009).

**Totals:** 53 findings — 15 High, 25 Medium, 13 Low. No Critical-rated findings: every High is either bounded by a precondition (LAN position, a click, a weak password) or is a data-protection failure rather than an instant remote compromise. That should not breed complacency — the preconditions (students on the LAN, teachers clicking student links) are the *normal operating environment* of this app.

## 2. System and deployment overview (as audited)

- **Runtime:** single Flask + Flask-SocketIO process (threaded mode, `simple-websocket`), Werkzeug server, port 8000, `HOST` default `0.0.0.0` (`start.sh` production path does not set it). No reverse proxy in code; no TLS in code.
- **Exposure:** Cloudflare Tunnel (`cloudflared`) publishes `https://code.mrgodwin.com`. The same process is directly reachable on the classroom subnet (192.168.0.1/22) and routable from the wider school network (10.144.0.0 range) at `http://<server>:8000`.
- **Auth model:** in-memory token maps (`_admin_tokens`, `_teacher_tokens`, `_student_tokens`); clients send `X-Admin-Token` / `X-Teacher-Token` / `X-User-Token` headers (HTTP) or token payloads (Socket.IO). Tokens are `uuid4().hex` (128-bit). A Fernet-encrypted device cookie (14-day) can restore a session. No Flask sessions, no `SECRET_KEY`.
- **Roles:** admin (single shared account, bootstrapped credentials in `config.txt`, Fernet-encrypted with `.admin_key`), teachers (accounts, own classes), students (accounts, class membership by join code), CoTeachers (students promoted per-class, subset of teacher rights on explicitly flagged routes), guests (limited IDE access subject to admin/class settings).
- **Execution:** student Python via `sandbox_worker.py` (Landlock filesystem containment, audit hooks, module policy, rlimits); student JavaScript via Node `vm` in `js_worker.js` (no OS containment); HTML runtime serves workspace files, with scripts enabled only on an operator-attested isolated preview origin.
- **AI:** all generation via a shared dispatcher to Ollama at an admin-configured URL (checked-in default `http://192.168.0.105:11434`, plaintext HTTP on the LAN).
- **Data stores (all inside the app tree, plaintext unless noted):** `users.json`, `classes.json` (incl. accommodations), `skills.json`, `assignments/` + `assignment_submissions/` (submissions, grades, feedback, quiz answers), `assignments/.development/*.sqlite3` (keystroke-level edit recordings keyed by student email), `notebooks/` (student notebooks, practice data, queue journal), `user_files/<email-derived>/` (workspaces, Trash, photos), `file_provenance/` (paste-range sidecars), `wiki_data/wiki.db` + media, `wiki_backups/*.zip`, `network_data/`, `lesson_plans/` (incl. public share tokens), `tool_data/` (gateway catalog + per-account tool storage), `challenge_scores.json`, `classroom_events.json`, `classroom_signals.json`, `sign_in_events.json`, `server.log`, `config.txt` (admin creds Fernet-encrypted), `.admin_key`.

## 3. Threat model

| Attacker | Access | Motivation/capability notes |
|---|---|---|
| **A — Internet stranger** | Via Cloudflare Tunnel only | Opportunistic scanning, credential guessing, abuse of open endpoints. Sees Cloudflare edge protections. |
| **B — Student on school LAN** | Direct HTTP to port 8000 + a student account (or self-registered one) | The realistic primary adversary: curious, skilled (they are *taught* Python/JS/HTTP here), physically present daily, knows teacher names, class routines, and when links will be clicked. Bypasses Cloudflare entirely. |
| **C — Malicious authenticated student** | B + a legitimate account in a class | Can plant files via code execution, share notebook content to classmates, submit crafted work. |
| **D — Process/accident** | No attacker | `git add -A` on the production checkout, a copied project folder, an over-broad backup share, a departing teacher. For a system holding minors' data, D causes the most likely bulk disclosure. |

**Assets, in impact order:** admin credential → all accounts; teacher tokens → class rosters, grades, submissions; student PII (names, emails, student IDs, accommodations); student work (code, notebooks, photos incl. EXIF location); keystroke-level development recordings; grades/feedback integrity; availability of the app + Ollama host during class.

## 4. Risk methodology

Each finding is scored **Likelihood (1–5)** × **Severity (1–5)** under the deployment as it actually exists (LAN-reachable, tunnel-published, used daily by minors).

- Likelihood: 1 = requires multiple unlikely preconditions; 3 = achievable by a motivated student with ordinary tooling; 5 = trivially and reliably exploitable today, or a condition that already exists.
- Severity: 1 = cosmetic/info; 3 = single-class data exposure, one-account takeover, or meaningful availability loss; 5 = full admin compromise, school-wide minors' PII disclosure, or total sandbox escape.
- Bands: 1–4 **Low**, 5–9 **Medium**, 10–16 **High**, 17–25 **Critical**.

For data-protection findings (retention/erasure), likelihood reflects how certain the harm is to materialize over the system's operating life (a parent erasure request, an audit, a folder copy), not the probability of an external attack.

## 6. Findings — deployment edge, authentication, sessions

### EAG-SEC-001 — Client IP is derived from spoofable forwarded headers (High, L4×S3)

**Evidence.** `app.py:1359-1383`, `_get_request_ip()`: if the direct peer (`remote_addr`) is private/loopback, the function trusts `CF-Connecting-IP` (returned without even requiring it to be a public IP), then the first public `X-Forwarded-For` entry, then any XFF entry, then `X-Real-IP`. The design intent — "trust headers only when the peer is proxy infrastructure" — collapses in this topology: **every** request qualifies. Tunnel traffic arrives from cloudflared on loopback (private), and every LAN client also presents a private address. The code cannot distinguish "header set by cloudflared" from "header set by the student sitting next to the server."
**Consumers (verified):** registration rate limit (120/hr/IP, `app.py:156`), AI rate-limit key (`app.py:5797`), Socket.IO per-IP connection/run tracking (`app.py:8197, 8715`), guest run caps, sign-in event logging (`app.py:2643, 2791, 2875`).
**Scenario (B/C).** A student adds `CF-Connecting-IP: <random public IP>` to each request and rotates it: unlimited registrations, per-IP guest/AI/socket limits never trigger, and sign-in logs can be framed onto a classmate's or the server's own IP. Internet traffic (A) is not affected the same way because Cloudflare overwrites `CF-Connecting-IP` at the edge — this is a LAN-side hole in exactly the controls meant to restrain LAN users.
**Fix.**
- Split the function: `_get_peer_ip()` (always `remote_addr`, used for LAN-direct requests) and `_get_client_ip()` used only when the peer is the known tunnel endpoint.
- Only honor forwarded headers when `remote_addr` is loopback **and** the deployment is configured tunnel-only (see EAG-SEC-002). For any non-loopback peer, ignore all forwarded headers unconditionally.
- Longer term, prefer Cloudflare Tunnel's authenticated origin model: have `cloudflared` inject a shared-secret header (or use mTLS/Access service tokens on the origin pull) and key trust on that, not on address class.
**Trade-offs / negative effects.** If the app is ever legitimately placed behind another LAN reverse proxy, that proxy's clients will all appear as the proxy IP, collapsing per-IP limits into one bucket — acceptable, and configurable via an explicit `TRUSTED_PROXY_IPS` setting (default: loopback only). Sign-in log IPs for LAN users become their real LAN IPs (more accurate, marginally more identifying in logs — see EAG-SEC-021).
**Preserve.** Tunnel users must still resolve to their real public IP for the registration limit and logs; add a test with a loopback peer + `CF-Connecting-IP` asserting the header is honored, and a test with a private-LAN peer asserting it is ignored.
**Acceptance tests.** New unit tests for `_get_request_ip` covering: loopback peer + header (honored), private peer + header (ignored), public peer (headers ignored), malformed headers (ignored).

### EAG-SEC-002 — Dev server bound to all interfaces; plaintext HTTP; no sign-in throttling; no admin IP allowlist (High, L3×S5)

**Evidence.** `app.py:13282-13283` `host = os.environ.get("HOST", "0.0.0.0")`; `app.py:13315` `socketio.run(app, host=host, port=port, debug=False, allow_unsafe_werkzeug=True)`; `start.sh:237` logs `0.0.0.0` and never sets `HOST` (the `AGENTS.md` manual-dev path uses `HOST=127.0.0.1`; production does not). Admin auth is token-only (`_require_admin`, `app.py:730-732`); a repo-wide search for any IP allowlist returns zero matches. Sign-in attempts are *intentionally* not rate-limited (`app.py:153-160`, rationale: classroom NAT); the only brake is an 8-concurrent password-check semaphore. Admin login comparison is `hmac.compare_digest` against a plaintext in-memory value (`app.py:2650-2662`) — no bcrypt cost — so admin guesses run at full HTTP speed. No `ssl_context`, no HSTS anywhere in code.
**Scenario (B).** Any device on the classroom subnet — or anything routed on the wider school network — can reach `http://<server>:8000/api/admin/login` and every `/api/admin/*` route directly, in plaintext, bypassing Cloudflare WAF/bot/rate-limit protections entirely, and guess the single shared admin password indefinitely. The same plaintext path exposes teacher/student bearer tokens and all student work to passive LAN sniffing or MITM. Werkzeug's dev server is additionally not hardened for hostile traffic (the `allow_unsafe_werkzeug=True` flag is an explicit acknowledgement).
**Fix (defense in depth — implement all four).**
1. **Bind loopback in production.** In `start.sh`, default `HOST=127.0.0.1`; the tunnel becomes the sole ingress. If direct LAN access is a deliberate feature (e.g., tunnel-outage fallback), document that decision and apply items 2–4.
2. **Host firewall** (deployment, §10 checklist): allow 8000 only from loopback and, if LAN access is retained, only the classroom VLAN — not the whole school network.
3. **Per-account sign-in throttling that tolerates shared NAT:** progressive delay + temporary lockout keyed on `(account, peer IP)` *pair* plus a global per-account failure counter (e.g., 10 failures → 5-minute lock for that account regardless of source). This refutes the NAT objection: a classroom of students behind one NAT does not produce 10 failures *on one account*. Apply to admin, teacher, and student logins; count with the real peer IP (EAG-SEC-001).
4. **Admin-route network guard:** a `before_request` check rejecting `/api/admin/*` and `/api/auth/admin-login` from non-allowlisted peers when an allowlist is configured (default: loopback + owner's admin IPs).
**Trade-offs / negative effects.** Loopback binding removes the "type the LAN IP when the tunnel is down" fallback — mitigate by keeping a documented, firewall-scoped LAN exception or a second loopback-only admin path. Account lockouts can be weaponized to lock a teacher out before class (DoS-by-lockout) — mitigate with the pair-keyed delay as the primary control, lockout only on the global counter, and an admin unlock path. Progressive delays slow the legitimate "30 students sign in at once" burst minimally if keyed per account (each student is a distinct account).
**Preserve.** The 8-concurrent password-check semaphore stays (it protects CPU); throttling is additive. Guest/IDE access flows unchanged.
**Acceptance tests.** Integration test: 11 failed admin logins from one peer → 429/locked; 11 failures spread across accounts from one IP → no lockout of other accounts; correct login during another account's lockout succeeds. Config test: `start.sh` dry-run prints `127.0.0.1` by default.

### EAG-SEC-003 — Student/teacher login: enumeration oracle + timing channel, no throttling (Medium, L3×S3)

**Evidence.** `/api/auth/login` (`app.py:2888-2918`) returns distinct error codes per failure mode — `account_not_found` ("No account was found for that email"), `account_disabled`, `incorrect_password`. Unknown-email requests return before any bcrypt work; known-email requests pay full bcrypt (~250 ms) — an explicit *and* a timing oracle. No throttling (see EAG-SEC-002 fix, which covers this endpoint too).
**Scenario.** Attacker confirms which emails have accounts (harvested from EAG-SEC-015's leaderboard, or guessed from school email patterns), then sprays passwords — composed with 6-character minimums (EAG-SEC-011) and 6-character temp passwords (EAG-SEC-006), this is the practical account-takeover path for student accounts.
**Fix.** Unify the failure response (`ok=False, code="invalid_credentials"`, one message) for not-found and wrong-password; keep `account_disabled` distinct only *after* a correct password (or return the same generic error and show the disabled notice post-auth). Perform a dummy bcrypt verification against a fixed hash for unknown emails to flatten timing. Apply EAG-SEC-002 throttling.
**Trade-offs.** Generic errors make classroom troubleshooting slightly harder ("did I typo my email or my password?") — acceptable; teachers can see account existence in their roster. Dummy bcrypt adds ~250 ms CPU to unknown-email attempts — bounded by the existing semaphore.
**Preserve.** Disabled-account UX must still surface *something* actionable for legitimate users; sign-in event logging keeps the true failure reason server-side.
**Acceptance tests.** Timing test (loose bound) that unknown-email and wrong-password responses are indistinguishable in body and code; log still records the distinct reason.

### EAG-SEC-004 — Access tokens never expire server-side; sessions accumulate (Medium, L3×S3)

**Evidence.** `_issue_access_token` (`app.py:1072-1081`) stores bare user info — no issued-at/TTL field exists in any token record (`app.py:437, 808-809`). Every login mints a new token without revoking the user's previous tokens. Repo-wide grep confirms no token expiry logic. A token remains valid until that exact token's logout, a password change/reset, account disable/delete, or server restart.
**Scenario.** A token stolen once (XSS — EAG-SEC-053; a shared device left signed in; a screenshot of devtools) is exploitable for the whole server uptime window, which for a school server can be months.
**Fix.** Add `issued_at`/`last_seen` to token records; enforce an absolute lifetime (suggested: 12 hours for students/teachers, 8 hours admin) and an idle timeout (suggested: 4 hours, refreshed on use — cheap in the token lookup helpers). Cap concurrent sessions per account (e.g., 5; evict oldest). Reuse the existing revocation paths.
**Trade-offs.** Long-lived classroom sessions will start expiring mid-week; students will need to sign in more often — mitigate with the device-cookie restore flow (EAG-SEC-005) so re-entry is one click on personal devices, and pick lifetimes that comfortably span a school day. Idle tracking adds a write on each authenticated request (in-memory dict — negligible).
**Preserve.** CoTeacher token semantics (teacher-token map carrying a student identity) must keep working; the session-restore validation flow (`app-core.js`) must handle the new "expired" response distinctly from "invalid."
**Acceptance tests.** Unit tests: token older than absolute TTL rejected; idle token rejected after timeout but accepted with activity; 6th concurrent session evicts the 1st; password change still revokes all.

### EAG-SEC-005 — Device cookie is a self-renewing, effectively perpetual bearer credential (Medium, L2×S4)

**Evidence.** `AUTH_DEVICE_SESSION_SECONDS = 14 days` (`app.py:161-162`). The cookie payload is Fernet-encrypted JSON containing role, email, a SHA-256 credential fingerprint, **the raw access token**, and expiry (`app.py:1028-1065`). `/api/auth/restore` (`app.py:2920-2958`) validates it, then re-issues the *same* embedded token and re-sets the cookie with a **fresh 14-day expiry** — sliding renewal with no absolute cap, and restore re-registers the token server-side, so the session even survives server restarts. `Secure` is set only when the request looks like HTTPS (`app.py:1055`, from the client-supplied `X-Forwarded-Proto`); over direct LAN HTTP the cookie traverses the network in cleartext (it is encrypted at rest in the cookie, but the blob is replayable as-is).
**Scenario.** Cookie theft (endpoint malware, browser-profile copy, shared-device residue) yields a session that renews itself indefinitely; the only revocation is a password change (via the fingerprint — a genuinely good control, keep it).
**Fix.** Add an absolute device-session lifetime (e.g., 30 days from first issue, stored in the payload as `first_issued_at` and never extended); shorten the sliding window on shared-device-sensitive roles (admin: no device cookie at all, or 1 day). Set `Secure` based on the *deployment mode* (tunnel/HTTPS expected) rather than per-request headers; when EAG-SEC-002's loopback binding lands, LAN-HTTP cookie exposure disappears with it.
**Trade-offs.** Students on personal devices re-authenticate monthly instead of never — minor. Removing the admin device cookie adds friction to the owner's daily use; that's the point, but make it a config flag so the owner chooses consciously.
**Preserve.** The credential-fingerprint invalidation on password change; HttpOnly + SameSite=Strict; the strict payload validation on restore.
**Acceptance tests.** Restore with `first_issued_at` older than the cap → rejected + cookie cleared; restore within caps → renewed with the *same* absolute deadline (assert the deadline does not move).

### EAG-SEC-006 — Admin-issued temporary passwords are 6 characters and are never force-changed (High, L4×S3)

**Evidence.** `/api/admin/users/reset-password` (`app.py:4284-4319`) generates 6 characters from a ~57-symbol alphabet via `secrets` (~35 bits). The comment claims "Students are prompted to replace it after sign-in" — a repo-wide grep for `must_change`/`force_change` finds **no such flag or flow anywhere**. The teacher reset path (`app.py:5563-5588`) inconsistently uses `secrets.token_urlsafe(16)` (~128-bit). Positive: admin reset revokes the victim's existing tokens (`app.py:4310-4317`).
**Scenario.** Temp passwords are spoken aloud and written on whiteboards/paper in real classrooms. A 6-character credential that is never rotated is guessable (especially through the unthrottled login, EAG-SEC-002/003) and observable, and there is no mechanism that ever forces it to change.
**Fix.** (1) Generate temp passwords with the teacher path's `secrets.token_urlsafe(16)` (or a readable 12-char grouped format if teachers must read them aloud — entropy ≥ 60 bits). (2) Add a real `must_change_password` flag on the user record: set by admin/teacher resets, checked at login; the API returns a restricted session (only `/api/auth/change-password` + logout callable) until the password is changed; the frontend forces the change screen. (3) Apply the same flag to newly created accounts with admin-set passwords.
**Trade-offs.** Longer temp passwords are harder to dictate in class — the grouped-readable format mitigates. A forced-change flow adds a login edge case every client must handle (frontend + any API consumers); test the restricted session carefully so students can't get permanently stuck (teacher must be able to re-reset).
**Preserve.** Token revocation on reset; the teacher-reset path's behavior converges to the same helper.
**Acceptance tests.** Reset → login with temp password → all non-password endpoints 403 with `password_change_required` → change password → full access; flag cleared in `users.json`; old temp password dead.

### EAG-SEC-007 — Open internet self-registration with unverified email and student ID (Medium, L4×S2)

**Evidence.** `registration_enabled` defaults to `True` (`config.py:66`, `app.py:316`). `/api/auth/register` (`app.py:2782-2870`) requires a `student_id` but validates only its presence (`app.py:2802-2806`); no email verification flow exists anywhere (grep-verified). Registration is rate-limited per IP (120/hr) — but see EAG-SEC-001 for that limit's LAN bypass.
**Scenario.** Anyone on the internet can mint an account under a real student's name/email/ID before the student does (the real student then hits "Email already registered," `app.py:2856-2857`), obtain a disposable authenticated identity for join-code guessing (EAG-SEC-012) and leaderboard harvesting (EAG-SEC-015), and bulk-create junk accounts.
**Fix (choose per deployment reality).** Preferred for a single-teacher deployment: default `registration_enabled` to `False` and create accounts via roster import/admin creation (the admin tooling already exists). If self-registration must stay (first-week-of-school practicality), require a valid class join code *at registration* (account is created already enrolled, code acts as the shared secret), and validate `student_id` format against an admin-supplied roster when one exists. Add an admin "pending accounts" view either way.
**Trade-offs.** Roster-first enrollment adds teacher prep work before day one and a failure mode for transfer students mid-year — mitigate with the join-code-at-registration variant, which keeps self-service but binds it to a classroom secret.
**Preserve.** The per-IP registration limit (with EAG-SEC-001 fixed) and the atomic duplicate-check inside the users lock (`app.py:2820-2860`).
**Acceptance tests.** Register without a join code → rejected when the setting requires it; register with a valid code → enrolled in exactly that class; duplicate email still rejected atomically.

### EAG-SEC-008 — Legacy plaintext passwords persist for dormant accounts (Medium, L2×S3)

**Evidence.** `_verify_user_password` (`app.py:990-1007`) still accepts a legacy plaintext `password` field (compared with `==`, not constant-time) and auto-upgrades to bcrypt only on that user's next successful login (`app.py:968-988`). Dormant accounts therefore carry recoverable plaintext credentials in `users.json` indefinitely.
**Fix.** One-time migration script (run once, by the admin, from the server console): for every record with a plaintext `password` field, replace it with a bcrypt hash of that same password (hashing the known plaintext preserves the user's password while removing the recoverable copy), or — for accounts inactive > 1 year — delete the field and mark the account `must_change_password` with a random temp (converges with EAG-SEC-006). Then remove the plaintext branch from `_verify_user_password`. Log a *count only* (never the emails) of migrated records.
**Trade-offs.** Hashing-the-plaintext keeps a weak password weak (just no longer recoverable from the file); the forced-reset variant is stronger but locks out dormant users until a teacher resets them — for a school, the summer break makes this a natural annual maintenance task.
**Acceptance tests.** Fixture `users.json` with legacy records → after migration, no `password` field anywhere; migrated users can still log in with the same password (hash variant); verify path no longer references the plaintext field.

### EAG-SEC-009 — Default admin password `"password"` checked into public source (Medium, L1×S5)

**Evidence.** `config.py:1-2`: `DEFAULT_ADMIN_PASSWORD = "password"`, `ADMIN_EMAIL = "audit-contact@example.invalid"`; import-failure fallback also defaults to `"password"` (`app.py:277`); module global set from it (`app.py:659`). **Why it is not live today (verified):** `_bootstrap_admin_credentials()` (`app.py:686-717`) runs at import and overwrites the password on every path (stored Fernet creds, else interactive prompt, `RuntimeError` after 10 failed attempts). The `AGENTS.md` non-interactive pre-seed recipe is exactly where a copied default could silently land, and the test suite itself stubs `getpass` to return `"password"` in several files.
**Scenario.** Any alternate entry point, seeding script, test-derived deployment, or future refactor that skips bootstrap activates a **publicly known** admin password on an internet-exposed login.
**Fix.** Delete the default value entirely: `DEFAULT_ADMIN_PASSWORD = None`; startup refuses to serve (clear error) if no admin credential source exists (config.txt encrypted creds, `ADMIN_PASSWORD` env, or interactive prompt). Replace test stubs' `"password"` with an obviously-fake fixture value. **Owner action (2 minutes, do first):** verify the production `config.txt` contains a real `admin_password_encrypted` produced by the bootstrap — i.e., confirm the deployed admin password is not any documented value.
**Trade-offs.** Fresh non-interactive installs fail loudly until seeded — that is the intent; update the `AGENTS.md` recipe to generate a random password in the seeding snippet.
**Acceptance tests.** Startup with no credential source → exits with the new error; startup with env-provided password → admin login works with it and `"password"` does not.

### EAG-SEC-010 — Admin password stored reversibly; key co-located (Low, L1×S4)

**Evidence.** Admin credential is Fernet-*encrypted* (reversible) in `config.txt`, decrypted into an in-memory plaintext global for comparison (`app.py:656-657, 695-696`); `.admin_key` sits in the same `BASE_DIR` (`app.py:259, 264, 662-672`); an existing key file is read back with no permission check/repair, and a failed `chmod 0o600` on creation is silently swallowed.
**Scenario.** Anyone who can read the app directory (backup leak, over-broad share, another local process) recovers the *actual admin password*, unlike bcrypt user hashes which still need cracking.
**Fix.** Store a bcrypt hash of the admin password (like user accounts) and verify with `bcrypt.checkpw`; keep Fernet only where reversibility is genuinely required (the device cookie). Migration: on first boot after the change, if a Fernet value exists, decrypt once, hash, overwrite. Repair key-file permissions on load (chmod if broader than 0o600, warn in log).
**Trade-offs.** The admin password becomes unrecoverable if forgotten — reset requires the bootstrap prompt path with server console access (already the documented flow). Slight login latency (~250 ms bcrypt) on admin login only — also a *benefit* against EAG-SEC-002 guessing.
**Acceptance tests.** `config.txt` after migration contains no decryptable admin password; admin login succeeds/fails correctly; tampered hash → login fails closed.

### EAG-SEC-011 — Inconsistent, weak password policy (Low, L2×S2)

**Evidence.** Minimums: student registration 6 chars (`app.py:2817`), teacher creation 8 (`app.py:4265`), self-service change 8 (`app.py:5599, 5633`). Maximum 72 UTF-8 bytes enforced (bcrypt limit — good). No composition rules or breached-password screening anywhere.
**Fix.** One shared validator: minimum 8 for all roles (10 for teacher/admin-set), maximum 72 bytes, and a bundled top-10k common-password blocklist check (offline list, no external service — do not send passwords anywhere). Apply at registration, creation, reset, and change.
**Trade-offs.** Younger students will pick simpler-to-type passwords within the rules; the blocklist catches the worst (`password1`, school mascot variants are worth adding locally). Slightly more "my password was rejected" moments in week one.
**Acceptance tests.** Each entry point rejects a 7-char and a blocklisted password, accepts a valid one; error messages identical across endpoints.

### EAG-SEC-012 — Class join codes: ~31-bit, unthrottled, never rotate (Low, L2×S2)

**Evidence.** `_generate_join_code` (`app.py:1176-1183`): 6 chars from a 36-symbol alphabet via `secrets` (~31 bits, good RNG, low entropy). The join route (`app.py:4569-4610`) has no rate limit (the rate-limit helpers are wired only into registration). Codes never rotate unless a teacher regenerates them, and in practice are shared verbally and written on whiteboards.
**Fix.** Throttle join attempts per account (e.g., 10 failed joins/hour → cooldown) and log failures; lengthen new codes to 8 chars; add an optional per-class "join requires teacher approval" flag that parks joiners in a pending list.
**Trade-offs.** Longer codes are slightly harder to dictate; approval queues add teacher clicks during the first week. Keep regeneration one click.
**Acceptance tests.** 11th failed join within the window → 429; successful join unaffected; regenerated code invalidates the old one immediately.

### EAG-SEC-013 — AI endpoints usable by unauthenticated callers (Medium, L3×S2)

**Evidence.** `_effective_ai_enabled` (`app.py:2596-2621`) ends with `return True, None` for any requester who is neither student nor teacher — the `guest_ide_access_enabled` flag is never consulted. `/api/explain` (`app.py:6275-6321`) has no server-side rate limit (it returns a client-facing random 30–90 s "cooldown" number *after* the call). `/api/assistant/chat` (`app.py:6614-6655`) enforces a 15 s cooldown keyed on the **client-supplied** `X-SID`/`sid` — freely rotatable.
**Scenario.** Anyone on the internet can drive the school's Ollama instance through the tunnel: GPU/CPU exhaustion that degrades or denies AI features (and heats/loads the host) for real classes, plus unrestricted anonymous use of the model.
**Fix.** Require an authenticated student/teacher/admin token (or an explicitly enabled guest-AI setting, default off) in `_effective_ai_enabled`. Key all AI cooldowns/rate limits server-side on the authenticated identity (or on the real peer IP for genuine guests), with per-identity and global concurrency caps routed through the existing shared dispatcher.
**Trade-offs.** If guests-with-IDE-access legitimately use the explainer in some class, they lose it unless the admin enables guest AI — surface that as an explicit admin toggle so the choice is conscious.
**Preserve.** The shared dispatcher and its overload cooldown behavior; notebook-practice and grading flows (already authenticated) unchanged.
**Acceptance tests.** Unauthenticated POST to both endpoints → 401; authenticated student → works and second rapid call is throttled by server-side identity even with a rotated `X-SID`.

## 7. Findings — student data at rest, privacy, retention & erasure

### EAG-SEC-014 — All identity PII is plaintext at rest; the public "encrypted" claim is false (High, L3×S4)

**Evidence.** `users.json` records (`app.py:260`; shape `app.py:2830-2846`; `_normalize_user_record` `app.py:859-884`; `_save_users` `app.py:951-958`) contain per student: email, bcrypt password hash, name/first/last name, `student_id`, `last_sign_in`, `last_ip`, class memberships, `tool_storage_id` — written via atomic tmp+replace with **no encryption and no chmod**. A codebase-wide search finds exactly two `Fernet.encrypt()` uses: the admin password in `config.txt` and the device-session cookie. The key for both (`.admin_key`) lives in the same directory as the data. Meanwhile the live Wiki Information page tells students/parents that names and emails are encrypted. **That statement is false as implemented** — independent of the code fix, the sentence itself is a compliance and trust exposure and should be corrected on the site immediately.
**Scenario.** Anyone who can read the server filesystem, an LXC/VM snapshot, a copied project folder, or a backup share obtains every student's name, email, and student ID in cleartext. Systemic amplifier: the only `chmod` in the entire codebase is on `.admin_key`; every data file/directory takes umask defaults.
**Fix.** Two layers, in order:
1. **Filesystem layer (biggest real-world win, least code):** set explicit permissions on all runtime data — data directories `0o700`, data files `0o600` — via a single `_ensure_private_path()` helper used by every store's save path, and run the service under a dedicated OS user (converges with EAG-SEC-030's runner user). Document in `AGENTS.md` that runtime data must live under the private tree.
2. **Honesty layer (immediate, zero code):** correct the Wiki Information page to describe reality ("access-controlled, stored on school equipment; passwords are hashed") until/unless field-level encryption lands. Only reinstate an encryption claim if names/emails are actually encrypted with a key stored *outside* the data tree (e.g., systemd credential / env-injected key) — field-level Fernet for `email`/`name`/`student_id` is feasible since lookups are by email (deterministic HMAC index needed for lookup; this is real surgery — treat as optional P2, not a precondition for closing this finding).
**Trade-offs.** `0o600`/`0o700` can break ad-hoc admin workflows (reading `users.json` as another user, backup jobs running as a different account) — the backup job must run as the service user or root. Field-level encryption (if pursued) complicates every roster sort/search and key rotation; do not let it delay layers 1–2.
**Preserve.** Atomic tmp+replace writes with locks (already the pattern — keep). Sort orders (last name, first name) and CSV export identifiers unchanged.
**Acceptance tests.** After any save, assert mode bits on `users.json`, `classes.json`, a notebook file, and a wiki backup are `0o600` (dirs `0o700`); app still passes the full suite running as the service user.

### EAG-SEC-015 — Leaderboard API discloses every student's email, cross-class (High, L5×S3)

**Evidence.** `_build_challenge_leaderboard` (`app.py:6443-6461`) iterates **all** users and returns `name`, `email`, `score`, `challengeCount` per row. The route `GET /api/challenge/leaderboard` (`app.py:6585-6592`) requires sign-in and class membership but never scopes rows to the requester's class. The frontend (`static/js/app-core.js:7428-7445`) displays only name + score — but the emails are in the JSON payload, visible to any student in devtools. *(Independently found by two audit streams.)*
**Scenario.** Any student in any class harvests the names and email addresses of students in *every* class — a school-wide directory disclosure of minors with no educational need, and a ready-made target list for the login attacks in EAG-SEC-003.
**Fix.** Build the leaderboard from the requester's class roster only (the class context is already resolved by the route), and drop `email` from the payload entirely (the UI never uses it). If a school-wide board is ever wanted for challenges, use display names + class labels, still no emails.
**Trade-offs.** A genuinely school-wide challenge board loses its cross-class rows; if the owner wants that feature, scope it to opt-in challenge events rather than the default class view. No other functional loss — the frontend doesn't consume `email`.
**Acceptance tests.** Two-class fixture: student in class A requests leaderboard → response contains only class-A students and no `email` key anywhere (recursive assertion).

### EAG-SEC-016 — Accommodations stored plaintext, keyed by student email (Medium, L2×S4)

**Evidence.** Accommodation entries live in `classes.json` under `accommodations[email]` (`app.py:1138`; `assignment_workflow.py:710`). Verified positives: a student sees only their own accommodations (`app.py:4972`); public lesson-plan payloads exclude them entirely.
**Scenario.** A `classes.json` disclosure exposes disability-adjacent (IEP/504) information linked directly to identity — among the most FERPA-sensitive data in the system.
**Fix.** Covered substantially by EAG-SEC-014's filesystem layer. Additionally: store *only* the operational parameters the app needs (deadline extension days, note for the teacher) — never diagnosis or plan details — and add an `AGENTS.md` rule to that effect; key the map by the opaque user key rather than email if the record layout is next touched.
**Trade-offs.** Minimization may frustrate a teacher who wants context in the note field; the deadline/note fields remain — the rule is about not recording *why*.
**Acceptance tests.** Existing assignment-workflow tests pass; student summary payload for another student contains no accommodation data (already true — pin it with a test).

### EAG-SEC-017 — Generic file uploads preserve EXIF/GPS metadata end-to-end (High, L4×S3)

**Evidence.** `POST /api/files/upload` (`app.py:3920-3930`) streams raw bytes to disk for all `ALLOWED_EXTENSIONS` including images (`app.py:206-208`); `GET /api/files/preview` (`app.py:3545-3556`) serves the original byte-for-byte. Contrast: the notebook-photo pipeline *does* strip metadata by re-encoding (`notebook_media.py:30-47`, test-pinned) — the protection exists in the codebase, it just doesn't cover the generic path.
**Scenario.** A student uploads a phone photo through Files (not the notebook button): full EXIF — GPS coordinates of the child's home, device serial, timestamps — persists at rest, is copied into submission bundles, and is downloadable by the teacher (and anyone the file is later shared with).
**Fix.** Route image uploads (by content sniff, not extension) through the same `photo_bytes()` re-encode used by `notebook_media.py` before the bytes touch disk: decode with PIL, `exif_transpose`, clear `info`, re-encode to JPEG/PNG with the existing pixel/dimension caps. Keep non-image types untouched. If a teacher genuinely needs original files (e.g., photography class), add a per-class "preserve originals" flag, default off, with a UI warning.
**Trade-offs.** Re-encoding loses original quality/format (PNG→JPEG for opaque images) and animated GIFs/WebP become static — the notebook pipeline already accepts these costs; the flag covers the exception. Upload CPU cost rises slightly (bounded by the existing 10 MB/25 MP caps).
**Acceptance tests.** Upload a JPEG with GPS EXIF via `/api/files/upload` → stored file has empty EXIF and decodes; upload via notebook path unchanged; non-image upload byte-identical.

### EAG-SEC-018 — Wiki media: raw storage + unauthenticated public serving, EXIF intact (High, L3×S4)

**Evidence.** Wiki uploads are validated by magic bytes only and moved verbatim (`wiki_store.py:1847-1850`); no PIL re-encode exists anywhere in `wiki_store.py`/`wiki_features.py` (grep-verified). The serving route `GET /api/wiki/media/<node_id>` (`wiki_features.py:239-254`) has **no authentication check**, `max_age=3600`, and echoes the original filename.
**Scenario.** A teacher uploads a class photo (or a photo of a field trip, a whiteboard with names) to the wiki; its GPS/EXIF is published to the open internet via the public site, indefinitely, under a guessable/enumerable node URL pattern shared in class.
**Fix.** Apply the same re-encode/strip pipeline as EAG-SEC-017 at wiki ingest. Keep public serving for genuinely public wiki media (that is the wiki's purpose) — the fix is metadata hygiene, not auth — but strip the original filename from the response (serve with a generic name) to avoid leaking camera-style filenames.
**Trade-offs.** Same re-encode costs as EAG-SEC-017; existing already-uploaded media is *not* retroactively stripped — include a one-time migration that re-encodes existing wiki media in place.
**Acceptance tests.** Upload EXIF-bearing image via wiki admin → public GET returns stripped bytes; migration script test on a fixture store.

### EAG-SEC-019 — Backups and admin exports are unencrypted (High, L3×S4)

**Evidence.** Wiki backups are plain ZIPs in `wiki_backups/` inside the app tree with default permissions (`wiki_store.py:229-237, 2277`), containing the full manifest — nodes, revisions, drafts, standards, `analytics_daily`, class features incl. teacher emails — plus soft-deleted content (soft delete only sets `deleted_at`, `wiki_store.py:1396-1404`). There is **no retention cap**: every restore also creates a `pre_restore_*.zip` (`wiki_store.py:2598`) that is never deleted, so the cleartext archive set grows monotonically. Separately, the dev-history admin export bundles the raw recording SQLite DB of **every** assignment into one unencrypted ZIP (`app.py:13253-13263` → `assignment_development.py:655-676`). (Positive: the backup *download ticket* mechanics are the model implementation in the codebase — admin-created, 300 s expiry, single-use, `no-store`, unlinked on close, `wiki_features.py:715-763`; restore itself is admin-only with manifest/schema validation, traversal rejection, per-file checksums, and rollback.)
**Fix.** Encrypt backup archives at creation (age or Fernet-based symmetric encryption with the key stored outside the data tree — see EAG-SEC-014; at minimum, write them `0o600` into a `0o700` directory outside the web tree). Add a retention policy: keep the newest N (e.g., 10) backups and newest 2 pre-restore archives, deleting older ones on creation. Require an explicit admin confirmation + reason string for the dev-history export, and log the export event (admin, timestamp) in `server.log`.
**Trade-offs.** Encrypted backups are unrestorable if the key is lost — the key must live in the owner's password manager/escrow (ties into the succession runbook recommended previously). Retention caps can delete a backup someone wanted; N=10 with restore-points preserved is a reasonable default.
**Acceptance tests.** Create 12 backups → only newest 10 remain; backup file mode `0o600`; restore from an encrypted backup succeeds in tests; export endpoint logs an event.

### EAG-SEC-020 — `assignment_submissions/` is missing from `.gitignore` in a public repo (High, L3×S5)

**Evidence.** `.gitignore` covers `users.json`, `classes.json`, `config.txt`, `.admin_key`, `notebooks/`, `user_files/`, `assignments/`, `wiki_data/`, `wiki_backups/`, `network_data/`, `tool_data/`, `lesson_plans/`, `file_provenance/`, logs, and sign-in events — but `assignment_submissions/` (per-class/assignment student submission content; default location `app.py:76-78`, listed as runtime data in `AGENTS.md:462`) appears **nowhere** in the file. Current state is clean (verified: `git status` clean, zero runtime files tracked across all 106 commits, no secrets in history). This is a loaded gun, not an existing exposure. *(Independently found by two audit streams.)*
**Scenario (D).** The owner (or a coding agent) runs `git add -A` / `git commit -a` on the production checkout to push a fix; every student's submitted work is published to public GitHub. Of all findings in this report, this is plausibly the *most likely* bulk-disclosure path over the repo's lifetime.
**Fix.** Add `assignment_submissions/` to `.gitignore` today (one line, zero risk). Belt-and-braces: add a `pre-commit` hook (or a CI check) that fails if any path matching the runtime-data list in `AGENTS.md` is staged; add a `git status` step to the repo's completion checklist (already advised in `AGENTS.md` — make it mechanical).
**Trade-offs.** None.
**Acceptance tests.** `git check-ignore assignment_submissions/probe.txt` returns the path; staging a probe file under it is blocked by the hook/check.

### EAG-SEC-021 — Sign-in log keeps full IPs; `server.log` unrotated; deleted users persist in logs (Medium, L3×S2)

**Evidence.** The sign-in event file stores full email + full unredacted IP (`app.py:265`; `_record_sign_in_event` `app.py:1293-1310`) — bounded by 90-day / 10,000-event retention (a positive, pruned at `app.py:1305-1306`) — while `server.log` redacts IPs via `_redact_ip_for_log` (`app.py:1333-1346`), an inconsistency. `users.json.last_ip` (`app.py:2000-2013`) never expires. `server.log` has **no rotation/truncation code anywhere** (grep-verified), and its sign-in lines include emails (`app.py:1311-1314`), so a deleted student's email persists in logs past every other retention window. Ad-hoc `print()` calls also write emails/exception text to the process journal outside the redaction discipline (`app.py:4438, 4445, 9646, 10248, 11942`). Verified positives: logs contain no tokens, student code, AI prompts, or request bodies; logs are not served by any route.
**Fix.** Apply `_redact_ip_for_log` consistently (sign-in events too — keep a full IP only if a concrete abuse-investigation need is documented, and then for 30 days, not 90). Add size-based rotation to `_append_server_log` (e.g., 10 MB × 5 files) or hand `server.log` to the OS logrotate under the deployment. Route the stray `print()` calls through the logging helper. On account deletion, no log scrubbing is required *if* rotation exists (bounded tail) — state that policy in `AGENTS.md`.
**Trade-offs.** Redacted IPs make abuse forensics coarser (subnet-level only) — for a school LAN that is usually sufficient and is the privacy-correct default. Rotation can drop the one old line you wanted during an incident; 5×10 MB is generous for this app's volume.
**Acceptance tests.** Sign-in event file contains redacted IPs; log file rotates at the cap in a unit test; grep test: no `print(` with an email variable remains in `app.py`.

### EAG-SEC-022 — Wiki analytics retains raw student search queries forever (Medium, L2×S3)

**Evidence.** `analytics_daily` keys include raw (case-folded, ≤200-char) student search queries (`wiki_features.py:234-236`) with **no pruning anywhere** (grep: no `DELETE FROM analytics_daily`). Wiki `bookmarks` (`owner_email, node_id, class_id, kind`, `wiki_store.py:512-522`) form a per-minor reading-interest record with no TTL and no account-deletion purge path (see EAG-SEC-025).
**Scenario.** Search queries by minors ("am I…", health, religion, family topics typed into a coding wiki) accumulate for years, keyed by day, exportable in every wiki backup (EAG-SEC-019).
**Fix.** Prune `analytics_daily` rows older than 180 days on backup creation (or a startup sweep like Trash's); aggregate query counts into a top-N with a minimum threshold (k-anonymity: drop queries with count < 3) or store a hash of the normalized query instead of raw text. Purge bookmarks on account deletion (add to the EAG-SEC-025 deletion manifest).
**Trade-offs.** Long-term trend analysis of rare queries disappears — acceptable; the feature is for spotting popular topics, which aggregation preserves.
**Acceptance tests.** Fixture rows older than the window are pruned by the sweep; low-count queries absent from admin analytics output.

### EAG-SEC-023 — Student work persists in browser `localStorage` on shared devices (Medium, L4×S2)

**Evidence.** Notebook drafts persist in `localStorage` (`static/js/student-notebook.js:203-206`); the assignment-development retry journal persists **full code frames** in `localStorage`, keyed by student email, 2 MB cap, removed only when frames+batch are both empty (`static/js/assignment-development.js:30-45, 54`). No logout/account-switch purge exists for either (grep-verified). (Contrast: auth tokens correctly live in `sessionStorage`.)
**Scenario.** Shared classroom devices: the next student to use the browser profile can read the previous student's drafts and unsynced code via devtools — and the data survives even server-side account deletion.
**Fix.** On logout and on account switch, clear the app-namespaced `localStorage` keys (drafts, retry journal, layout prefs scoped per account); before clearing the retry journal, attempt a final flush and, if it fails, warn the student their unsynced work will be discarded. Also add a "this device" note in the student help text.
**Trade-offs.** A student who logs out with unsynced work loses the offline-recovery safety net — the flush-attempt + warning covers the honest case; the journal exists for network outages *within* a session, which still works.
**Acceptance tests.** UI test: seed journal + draft keys, log out, assert keys absent; log back in as a different account, assert no prior-account keys readable.

### EAG-SEC-024 — Paste monitoring and edit recording are undisclosed to students/parents (Medium, L4×S2)

**Evidence.** The app records per-file paste ranges (`file_provenance.py` — ranges + whole-file SHA-256 only, **never content**: a genuine positive) and full keystroke-level development history for controlled assignments (`assignment_development.py`). Student-facing surfaces omit this: submission payloads hide `pasteRanges` (by design), and a grep of `index.html`/`static/js` finds **no student/parent-facing disclosure** of either the paste monitoring or the recording; the only accuracy disclaimer ("a paste event does not identify its source") is teacher-facing (`static/js/assignment-workflow.js:34`). A student's own file-read does return their ranges (`app.py:3427-3428`), so the data is not secret from a determined student — it is simply never *explained*.
**Scenario.** This is a COPPA/transparency and trust issue rather than a technical breach: minors are monitored with no in-product notice, and the flag is evadable (attachments, out-of-IDE edits), so any disciplinary reliance on it would be both undisclosed and unreliable.
**Fix (owner + small code).** Add a plain-language student/parent notice (wiki Information page + first-login acknowledgment): what is recorded (edit history on controlled assignments, paste *ranges* not clipboard content), who can see it (their teachers), how long it is kept (tie to EAG-SEC-027's expiry), and that it is an aid, not proof of misconduct. In the teacher UI, keep the existing disclaimer adjacent to any paste flag.
**Trade-offs.** Disclosure may marginally increase evasion attempts; it also legitimizes the tool and protects the school if use is ever questioned. No functional cost.
**Acceptance tests.** Notice present in the wiki seed content and linked from the student home/account page; acknowledgment flag stored per user.

### EAG-SEC-025 — Account deletion does not erase the student's data — and can falsely report success (High, L4×S4)

**Evidence.** Sole implementation: `admin_delete_user` (`app.py:4321-4332`) → `_delete_user_by_email` (`app.py:4396-4452`); bulk delete loops the same helper (`app.py:4455-4477`).
*What deletion does remove (verified):* `users.json` record, in-memory tokens, class rosters, the whole `user_files/<…>/` workspace incl. Trash and notebook images (`shutil.rmtree`, `app.py:4442`), `file_provenance/` sidecars (`app.py:4443`), external-tool storage by `tool_storage_id` (`app.py:4447-4449`), socket rooms. Path containment is checked before `rmtree`; the device cookie self-invalidates.
*What survives (verified):*
- **Submissions, scores, feedback, quiz answers** — the helper never references `ASSIGNMENTS_DIR`/`ASSIGNMENT_SUBMISSIONS_DIR`; submissions live in `assignments/<id>.json` `submissions[]` (email, name, code, scores, feedback, quiz responses) and `assignment_submissions/` (`assignment_workflow.py:315-341`).
- **Development recordings** — no `assignment_development.purge(...)` call; per-assignment SQLite DBs keyed by plaintext email (`assignment_development.py:107-115`), and the index (`assignments/.development/index.sqlite3`) retains bindings incl. the absolute workspace path after the workspace is gone.
- **Notebooks** — no deletion of `NOTEBOOKS_DIR/<class>/<email>.json` in account *or* class deletion (grep-verified); the practice-queue journal (`notebooks/.practice-queue.json`) keeps `(email, class_id, prompt_id, revision_id)` job identities forever.
- **Network-simulator data** — progress file bodies embed plaintext `student_email` + topology + grade (`network_store.py:883`); no delete-by-user exists.
- **Challenge scores** — `challenge_scores.json` retains name + scores (`app.py:6428-6441`); re-registering with the same email silently resurrects them.
- **Classroom signals** — `classroom_signals.json` has no retention/pruning at all (events in `classroom_features.py` are bounded 90 d/5,000 — a positive — but signals with `student_email`/`student_name`/question text, `classroom_features.py:75-90`, are not).
- **Wiki bookmarks / class features** keyed by email — no purge path.
- **Copies in other workspaces** — files a student sent to a teacher/peer, and shared notebook tabs, are independent copies deletion cannot recall (inherent; but the UI never discloses it).
*False-assurance defects:* `_save_users` and class saves commit (`app.py:4408, 4429-4430`) **before** the containment check; on `ValueError` the helper returns `False` (`app.py:4437-4439`) and the route reports **404 "User not found"** although the record and roster are already deleted and the workspace was never touched. Workspace `rmtree` failure is swallowed with a `print()` warning and the function still returns `True` (`app.py:4444-4445, 4452`). A failed tool-storage SQLite delete likewise only logs a warning while deletion reports success (`app.py:4450-4451`).
**Scenario.** A parent exercises erasure rights; the admin deletes the account and reports completion; the teacher can still open the student's full submissions, feedback, notebooks, and keystroke history indefinitely. No retention clock ever starts.
**Fix — implement deletion as a manifest-driven purge.** Create one `_purge_user_data(email)` routine (used by single delete, bulk delete, and teacher deletion in EAG-SEC-026) with an explicit store-by-store checklist, mirroring how `AGENTS.md` enumerates runtime data:
1. Reorder: validate containment for **all** paths first; mutate only after validation passes. Any store failure → return a structured partial-failure report (which stores failed) and a non-2xx status; never report success on partial purge, never report "not found" after mutation.
2. Purge/anonymize per store: submissions — remove the student's entries from each `assignments/<id>.json` and delete their `assignment_submissions/` files (or, where a grade record must be retained per school policy, replace name/email/code with a tombstone and keep only the score — make this an explicit owner policy flag `RETAIN_GRADES_ON_DELETE`, default purge-all); recordings — `assignment_development.purge` for the email across all assignment DBs + index bindings; notebooks — delete the student's notebook files for every class + scrub the practice journal; network data — delete progress/topology files and any embedded-email bodies; `challenge_scores.json` — remove the entry; classroom signals — remove the student's entries; wiki bookmarks — delete by `owner_email`.
3. Emit a deletion report (counts per store, no content) to `server.log` and return it to the admin UI.
4. Add the missing stores to the deletion tests (below) so future features must opt *in* to the manifest — add an `AGENTS.md` rule: "any new per-user store must register in `_purge_user_data`."
**Trade-offs / negative effects.** Purging submissions destroys grade-history a school may be obliged to keep — hence the policy flag; the owner must pick the retention rule consciously (and it interacts with EAG-SEC-029's backup decision: backups must honor the same purge or erasure is illusory — at minimum, backups containing the student must expire on the backup-retention schedule, EAG-SEC-019). Tombstoning preserves aggregates but complicates submission-list rendering (test it). Deleting shared-tab/file copies in *other* users' workspaces is deliberately out of scope — disclose it in the admin UI ("copies previously shared with others are not recalled").
**Preserve.** Everything deletion currently does right (tokens, workspace, provenance, tool storage, containment check) becomes manifest steps, not rewritten logic. Class-deletion's fail-closed pattern (assignment cleanup failure → 503 before removing the class row, `app.py:5219-5220`) is the model to copy.
**Acceptance tests.** Seed a student with data in *every* store; delete; assert absence (or tombstone) in each, including SQLite DBs and journals; fault-injection: make one store raise → response reports partial failure and the user record is not half-deleted; bulk delete behaves identically.

### EAG-SEC-026 — Teacher/class deletion orphans class data, including live public share tokens (High, L3×S4)

**Evidence.** Deleting a *teacher* (`app.py:4422-4427`) removes only their `classes.json` rows — it does not call `_delete_assignment_storage_locked`, `lesson_plan_store.delete_class`, or the per-student unassignment that class deletion performs (`app.py:5223-5229`). Orphaned: all assignments + submissions + recordings for that teacher's classes; every student's `notebooks/<class_id>/`; lesson plans **including live public share tokens** (`lesson_plan_store.py:422-439` is invoked only from class deletion, `app.py:5256`); `network_data` for the class; `skills.json` rows; students' stale `class_ids`. There is no UI path to delete the orphans afterward.
*Class deletion itself* (verified positives) purges assignments (metadata, submission files, dev DBs, bindings, folders), the class row incl. accommodations/join code, memberships/tokens/rooms, background assets, skills class IDs, and lesson plans + tokens + assets — with strict isolation and fail-closed assignment cleanup. **But** it leaves the class's **notebooks** behind entirely (no notebook step in `app.py:5192-5259`), plus `network_data`, wiki `class_features`/`bookmarks`, and the `classroom_signals.json` bucket. And its lesson-plan purge failure is *swallowed* (`app.py:5255-5258`, `try/except: pass`) — in contrast to the fail-closed assignment step — so a failed purge leaves media and a **valid public share token** behind while the class reports deleted.
**Fix.** Make teacher deletion iterate the teacher's classes through the *same* `_teacher_delete_class_locked` routine used by class deletion (one code path, no drift), then purge the teacher's own account stores via EAG-SEC-025's manifest. Extend class deletion with the missing steps: notebooks for the class, network-data class entries, wiki class features/bookmarks for the class, classroom-signals bucket. Change the lesson-plan step to fail closed like the assignment step (abort with 503, class row intact) or record a durable retry/task entry — do not swallow.
**Trade-offs.** Teacher deletion becomes slower and can now fail partway (a departing-teacher cleanup may need an admin retry) — the deletion report from EAG-SEC-025 makes that manageable. Deleting a teacher mid-year is destructive by definition; add an admin confirmation that lists what will be purged (counts) before executing.
**Acceptance tests.** Fixture: teacher with a class containing assignments, notebooks, lesson plan + live token, network progress → delete teacher → all stores empty for that class, token returns 404, other classes untouched; fault-inject the lesson-plan purge → class deletion reports failure and the class row survives.

### EAG-SEC-027 — Development recordings have no time-based expiry (High, L4×S3)

**Evidence.** `assignment_development.py` records a full, reconstructable source history (splices with verbatim inserted text, `assignment_development.py:145-160`; periodic full-content checkpoints, zlib-packed; `streams.content` always holds the latest full source), with both device and server timestamps. Volume is capped (2 MB source / 16 MB per stream / 512 MB total; checkpoint every 120 changes) and access is teacher/co-teacher only — but the *only* purge triggers are grading completion/finalize, assignment deletion, class deletion, and copy-assignment. If a teacher grades in the gradebook and never clicks "grading complete," every controlled-file student's complete edit history — deleted drafts, mistakes, pasted-then-removed text — is retained for **years**. Caps bound volume, not duration.
**Fix.** Add a time-based retention: recordings are purged N days after the assignment's effective deadline (or after finalization, whichever is first), with N an admin setting (default 90, i.e., past grade-appeal windows). Implement as a startup + daily sweep alongside the existing Trash purge call sites, and show each assignment's recording-retention date in the teacher UI so the purge is never a surprise. Keep the finalize-purge behavior unchanged.
**Trade-offs.** Late grade disputes/appeals after N days lose the edit-history evidence — the setting and the UI date make this a conscious policy choice; align N with the school's actual appeal window.
**Acceptance tests.** Fixture recording past the retention date → swept; recording within window → intact; finalize still purges immediately.

### EAG-SEC-028 — Trash purge is opportunistic; trashed files remain teacher-readable (Medium, L3×S2)

**Evidence.** Trash has a 7-day retention constant (`app.py:224-226`) and correct mechanics (move records provenance; purge removes provenance sidecars; permanent delete inside Trash is immediate; the Trash root is protected from rename/upload/delete). But purge runs only at server startup, on the *student's own* file-tree access, and on the teacher audit list (call sites `app.py:2444-2454, 3143`; `classroom_features.py:404`) — a long-running server plus a student who never reopens the file browser keeps Trash contents far past 7 days. Separately, the teacher audit tree/read (`classroom_features.py:398-410, 412-440`) has no Trash exclusion: a student who "deletes" a personal file has not hidden it from their teacher, and the UX never discloses that.
**Fix.** Add Trash purge to the same daily sweep as EAG-SEC-027. For the audit view, either exclude Trash or label it explicitly ("Trash — deleted by student, retained 7 days") so teacher visibility is a visible policy, not a surprise; add one line to the student file-browser help stating teachers can see Trash during the retention window.
**Trade-offs.** A daily sweep is one more background task (trivial cost at this scale). Labeling rather than excluding preserves the legitimate audit use (recovering "accidentally deleted" work is a real classroom need).
**Acceptance tests.** Expired Trash item purged by the sweep without any file-tree access; audit list shows the Trash label.

### EAG-SEC-029 — No backup exists for `users.json` / core student data (Medium, L2×S4)

**Evidence.** Repo-wide, the wiki system is the only server-side backup mechanism. Keep the snapshot restore procedure in the succession runbook, and test a restore once.
**Trade-offs.** Backups are also a privacy liability (they defeat erasure unless they rotate — the 14–30 day rotation is what makes EAG-SEC-025's purge meaningful; document that interplay). Storage cost is modest at classroom scale.
**Acceptance tests.** Documented restore drill: restore last night's snapshot into a scratch instance and sign in as a fixture user.

## 8. Findings — execution sandbox, HTML runtime, browser layer, AI flows, sharing

### EAG-SEC-030 — No OS-level network isolation for sandboxes; the JS runner has no OS containment at all (High, L2×S5)

**Evidence.** The Landlock ruleset in `sandbox_containment.py` grants **filesystem rights only** — no `LANDLOCK_ACCESS_NET_*` handling (Landlock network rules need ABI 4+; the deployment targets ABI 3). Repo-wide: no network namespaces, firewall rules, or seccomp anywhere (`unshare`/`setns`/`iptables`/`nft` — zero hits). Python's network block is entirely in-process: locked modules (`sandbox_policy.py:17`) plus the worker's audit hook blocking `socket.*`/`ctypes`/`os.exec*` events (`sandbox_worker.py`). The JS runner (`app.py` ~7955–7985) spawns Node with only `--max-old-space-size`, POSIX rlimits, process-group kill, and an allowlisted environment — **no Landlock, no chroot, no dedicated user, no network restriction**; `js_worker.js:18`'s `vm` context is the only barrier, and `AGENTS.md` itself states Node's vm is "defense in depth, not an OS security boundary." The vm hygiene itself is good (code-generation from strings/WASM disabled — killing `Function`-constructor escapes; frozen bridge/console; dynamic `import()` rejected with a realm-created Error; host paths redacted; regression tests in `tests/js_worker.test.js:25`), as is the Python sandbox (enumerated read-only Landlock grants that exclude the repo/data tree, `PR_SET_NO_NEW_PRIVS` before `restrict_self`, native modules fail closed below ABI 3, path-checked `open`/`sqlite3.connect`, defanged dangerous modules, strict env allowlist — server secrets are not inherited).
**Scenario.** If student JS escapes the vm (Node vm escapes are a recurring CVE class; the mitigations cover *known* patterns), the escaped code runs **as the Flask server's OS user** with unrestricted filesystem and network: read every student's workspace and the app's data directory, and reach LAN services — the Omada controller, Proxmox UI/API, the Ollama API (unauthenticated by default), and the open internet. The same applies to any future in-process Python escape, which likewise has no OS network backstop. Likelihood of the initial escape is low; impact is total. The missing layer is the finding.
**Fix (in order of leverage).**
1. Run both runners as a **dedicated unprivileged OS user** whose filesystem access is limited to the workspace/sandbox roots (converges with EAG-SEC-014's private-tree permissions — together they ensure an escape finds no readable PII).
2. Put runner processes in a **network namespace with no routes** (or, where the LXC topology makes that awkward, an egress firewall rule for the runner user: `nftables`/`iptables` owner-match drop, with an exception only if a future feature truly needs network). If the host kernel supports Landlock ABI 4+, add network rules to the Python worker as a third layer.
3. Keep the in-process controls exactly as they are — they remain the primary barrier; this finding adds the missing backstop.
**Trade-offs.** Namespaces inside an LXC need nesting privileges configured on the host (owner action; the launcher already reports Landlock status — extend it to report namespace capability and fail closed for JS if unavailable, mirroring the native-module fail-closed pattern). A dedicated runner user complicates workspace file ownership (files created by runs must be chowned/readable by the app user) — the runner script write/cleanup paths need care and tests. Firewall owner-rules are host config that must be captured in the deployment runbook or they silently vanish on a rebuild.
**Preserve.** All current limits (RLIMIT_AS 750 MB Python / heap 384 MB + 1.5 GB AS for JS, CPU/wall/output caps, admission control) and the fail-closed behavior for native modules without Landlock.
**Acceptance tests.** From inside a JS run and a Python run: attempt a TCP connect to 127.0.0.1:8000, to the LAN gateway, and to a public IP — all must fail at OS level (test asserts connection refused/unreachable, not merely module-blocked); attempt to read `users.json` from a run — must fail on permissions; normal runs (incl. NumPy/Matplotlib/SQLite) still pass `tests/test_python_sandbox.py` and `tests/js_worker.test.js`.

### EAG-SEC-031 — HTML runtime serves `.htm`/`.svg` script-live on the main origin: teacher token-theft chain (High, L3×S5)

**Evidence.** `view_html_runtime_asset` (`app.py:7124-7191`): only `ext == ".html"` receives CSP treatment; every other extension falls through to a bare `send_file(...)` with no CSP, no `Content-Disposition`, no extension allowlist. `send_file` serves `.htm` as `text/html` and `.svg` as `image/svg+xml` — both script-capable on direct navigation. `_is_html_file` (`app.py:782`) accepts `.htm` as a runtime *entry*, but the CSP branch checks only `".html"`, so even a legitimate `.htm` entry runs with **no CSP at all**, including in the scripts-disabled fallback mode that is supposed to guarantee `script-src 'none'`. The view route performs no host check — it answers on the main app origin even when an isolated preview origin is configured (isolation gating, `app.py:797`, covers only `.html` bridge/CSP). Global headers don't mitigate: `nosniff` is irrelevant for a top-level navigation to a correctly-typed document, `X-Frame-Options: SAMEORIGIN` doesn't block top-level navigation, and there is no global CSP (EAG-SEC-033). Planting the file is easy: the upload allowlist blocks `.svg`/`.htm`, but student **Python code can write any filename into its own workspace** (the worker's path policy restricts location, never extension). Auth tokens live in `sessionStorage` (`static/js/app-core.js:182-193`), readable by any script executing on the main origin in that tab.
**Scenario (C→teacher).** A student runs Python that writes `evil.svg` (SVG with an embedded `<script>`) into their workspace, starts an HTML runtime on any `.html` file to obtain a live runtime ID, and sends the teacher a link: `https://code.mrgodwin.com/api/html-runtime/view/<runtime_id>/evil.svg` ("my project page, can you check why it looks wrong?"). The teacher clicks during class; the script executes in the main origin and exfiltrates the teacher's session token → teacher account takeover (rosters, grades, submissions for all their classes). The window is the runtime TTL (≤600 s + 120 s grace ≈ 12 minutes) — realistic inside a class period. The `.htm` variant needs no SVG trickery.
**Fix.**
1. Serve runtime assets from an **allowlist of inert types** with explicit safe content types (`.css`, `.js` — as text with `nosniff`, images `.png/.jpg/.gif/.webp` only, fonts, `.json`/`.txt` as `text/plain`); everything else → `Content-Disposition: attachment` or 404.
2. Apply `Content-Security-Policy: sandbox` (or `default-src 'none'`) to **all** runtime asset responses as a backstop, including allowed types.
3. Treat `.htm` identically to `.html` everywhere (single `_is_html_file` check in the view handler).
4. When an isolated preview origin is configured, refuse to serve the view route on the main origin at all (redirect or 404) — the main origin should never render student HTML/SVG.
5. Exclude `.svg` from files a runtime can serve even if present in the workspace (SVG only ever as `<img>` from an inert-type response with `Content-Type: image/svg+xml` **plus** `Content-Security-Policy: sandbox` — or strip/re-encode per EAG-SEC-017's pipeline).
**Trade-offs.** Student projects that legitimately use SVG-as-document or exotic asset types served from the workspace will break (rare; SVG-as-image still works). Forcing the preview origin removes the convenience of main-origin previews in deployments that never configured isolation — those deployments currently get the risky behavior by default, so the breakage is the point; keep the scripts-disabled main-origin fallback for `.html` only, with its CSP.
**Preserve.** The runtime's capability model (uuid4 IDs, expiry, per-user/global caps), the bridge's fetch/XHR/navigation blocking, and scripts-enabled rendering **on the isolated origin**.
**Acceptance tests.** Runtime serving: `.svg` request → attachment or sandboxed response with CSP header asserted; `.htm` entry with scripts disabled → `script-src 'none'` asserted; `.html` on main origin with preview origin configured → refused; legitimate CSS/JS/image assets still load in the HTML-runtime test suite (`tests/test_html_runtime.py` extended).

### EAG-SEC-032 — HTML-runtime capability URL exposes the owner's entire workspace, including `.eagleide` private data (Medium, L2×S4)

**Evidence.** The view route authorizes on the `runtime_id` alone (uuid4; by design for the cookieless preview origin), but asset lookup uses `_validate_user_path` (`app.py:2456-2468`), which containment-checks yet does **not** exclude `.eagleide/` or Trash — unlike `_validate_workspace_path` (`app.py:2478-2492`). The personal notebook store lives inside the served root (`USER_FILES_DIR/<user>/.eagleide/personal_notebook.json`). Any workspace file ≤10 MB is readable through the capability: source, CSV data, notebook contents, trashed files. `POST /api/html-runtime/cleanup` is likewise unauthenticated (anyone with an ID can kill a preview — trivial, noted for completeness).
**Scenario.** A runtime URL leaks (browser history on a shared machine, a screenshot, a chat paste). For ~12 minutes, anyone holding it can enumerate and download the student's private notebook and every workspace file with no credential.
**Fix.** Scope runtime asset resolution with the `_validate_workspace_path` rules (exclude `.eagleide`, Trash) and further restrict served paths to the entry file's directory subtree. Keep the capability model itself (it is the right pattern for a cookieless preview origin) but shorten TTL toward the low end and surface active runtimes in the student's UI with a "stop sharing" control.
**Trade-offs.** Projects that reference assets outside the entry file's folder (e.g., `../shared/style.css`) will break — mitigate by allowing the workspace root as the subtree boundary but keeping the `.eagleide`/Trash exclusions absolute.
**Acceptance tests.** Runtime asset request for `.eagleide/personal_notebook.json` and for a Trash path → 404; sibling asset of the entry file → 200.

### EAG-SEC-033 — No Content-Security-Policy on the main application; no HSTS in code (Medium, L3×S3)

**Evidence.** The `after_request` hook (`app.py:394-423`) sets CSP **only** for `/lesson-plans/embed/*` paths (that policy's `frame-ancestors *` is intentional — it's the embed surface). All other paths get `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy`, `Permissions-Policy`, and `nosniff` only. Live check (2026-10-21) confirms the homepage response carries no CSP and no `Strict-Transport-Security`. Repo-wide grep for HSTS: zero hits (it may exist at the Cloudflare edge — unverified from code; see §10 checklist; LAN HTTP traffic gets no benefit regardless).
**Scenario.** Any stored/reflected XSS that slips past DOMPurify or escaping executes with no CSP backstop: no restriction on exfiltration endpoints, no `object-src`/`base-uri` defense. This is the force multiplier behind EAG-SEC-031/034/035/053.
**Fix.** Roll out a CSP for the main app in report-only mode first (the app uses inline styles and CDN scripts, so expect iteration): target policy ≈ `default-src 'self'; script-src 'self' https://cdn.jsdelivr.net https://cdnjs.cloudflare.com https://cdn.socket.io; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data: blob:; connect-src 'self' wss:; object-src 'none'; base-uri 'self'; frame-ancestors 'self'`. Move to enforcing after a report-only soak across all major views (IDE, wiki, notebook, network sim, tools). Enable HSTS at the Cloudflare edge (§10).
**Trade-offs.** CSP rollouts on a no-build-step, inline-heavy frontend always break *something* on the first pass (CodeMirror dynamic styles, chart libs, the external-tools frames) — hence report-only first, and keep the per-surface policies that already exist (wiki assets, tool gateway, embeds) untouched. Do not chase nonce-ification of every inline handler in this pass; origin allowlists are the pragmatic step.
**Acceptance tests.** Header assertions on `/`, a wiki page, and an API response; a scripted pass through the manual verification list in `AGENTS.md` with the enforcing policy and the browser console free of CSP violations.

### EAG-SEC-034 — Most CDN scripts load without Subresource Integrity (Medium, L2×S4)

**Evidence.** `index.html:17-47`: CodeMirror 5.65.16 (CSS + 14 JS files, cdnjs), Socket.IO client 4.7.5 (cdn.socket.io), highlight.js 11.9.0 (cdnjs) — **no `integrity` attribute on any**. `static/js/lazy-libs.js:5-17` dynamically injects Chart.js 4.4.3 and jsPDF 2.5.1 from jsDelivr with no integrity. The security-critical pair is done right: `marked@18.0.7` + `dompurify@3.4.7` carry `integrity="sha384-…"` + `crossorigin="anonymous"` (`index.html:35-40`; also `lesson_plan_public.html:12-13`). All versions are pinned (positive).
**Scenario.** Compromise of cdnjs/cdn.socket.io (or a DNS hijack on a network path) serves trojaned CodeMirror/Socket.IO to every user; injected script reads sessionStorage tokens (EAG-SEC-053) → mass account takeover. With no CSP script-src enforcement (EAG-SEC-033), nothing limits the payload.
**Fix.** Add SRI hashes + `crossorigin="anonymous"` to every CDN `<script>`/`<link>` in `index.html` and to the dynamic injections in `lazy-libs.js` (set `script.integrity` before append). Generate hashes from the pinned versions and record the regeneration step in `AGENTS.md` next to the version pins, so a future version bump updates both together.
**Trade-offs.** A CDN that serves a slightly different build (or a bad hash transcription) breaks the app for everyone until fixed — the failure is loud and immediate, which is preferable to silent compromise; keep the hashes in the same commit as any version change.
**Acceptance tests.** Static test (extend `tests/test_static_html.py`): every external script/link tag in `index.html` has a well-formed `integrity` attribute; `lazy-libs.js` sets integrity for both dynamic libs.

### EAG-SEC-035 — `renderHomeContent` fails open to unsanitized `innerHTML` (Medium, L2×S3)

**Evidence.** `static/js/app-core.js:2382-2390`: if `window.DOMPurify` exists the home content is sanitized; **else the raw stored HTML is injected via `innerHTML`**. The content (`notes_html` from `/api/config`) is admin-authored, capping direct risk — but the failure mode is silent: if the SRI-pinned DOMPurify asset fails to load (CDN outage, school content filter, SRI mismatch after a bad deploy), sanitization disappears for content rendered to every student. Sibling renderers fail *closed*: the wiki renderer falls back to `textContent` (`wiki-reader.js:1423-1426`), the lesson renderer returns `''` (`lesson-plan-renderer.js:11`).
**Fix.** Mirror the wiki behavior: without DOMPurify, set `textContent` (or render nothing with a visible error). Audit for any other `innerHTML` fallbacks with the same pattern while in the file.
**Trade-offs.** In the (rare) DOMPurify-missing case the home page shows raw markup as text instead of formatted content — a visible, safe degradation.
**Acceptance tests.** UI test with DOMPurify blocked: home content renders as text, no element injection.

### EAG-SEC-036 — Server-side notebook HTML sanitizer is regex-based (Medium, L2×S3)

**Evidence.** `_sanitize_notebook_html` (`app.py:1622-1633`) strips dangerous tags, `on*` attributes, and `javascript:` URLs via regular expressions — a known-bypassable pattern class (malformed/nested tags, unquoted attributes, SVG/MathML vectors, unenumerated attributes). Notebook HTML is persistent and shareable to classmates (`app.py:1921-1926`). **Mitigating (verified):** the client re-sanitizes with DOMPurify before display (`static/js/student-notebook.js:66-73`), and that path's no-DOMPurify fallback *escapes* — so exploitation today requires defeating DOMPurify, not just the regex.
**Fix.** Treat the server regex as a *storage hygiene* filter only (document that in a comment), and eliminate any present/future consumer that could render notebook HTML without the DOMPurify pass: grep for notebook-HTML consumers (exports, PDFs, teacher views) and route each through a server-side allowlist sanitizer (e.g., `bleach`-equivalent — evaluate adding a pinned dependency, or a strict tag/attribute allowlist built on `html.parser`) for any non-browser rendering.
**Trade-offs.** A real server-side sanitizer is a new dependency (or a chunk of careful code) and may strip exotic-but-legitimate notebook formatting the regex currently permits; the browser path is unchanged, so student-visible behavior should not change.
**Acceptance tests.** Sanitizer corpus test (OWASP XSS cheat-sheet payloads) for any server-rendered path; notebook UI tests unchanged and green.

### EAG-SEC-037 — AI data flows: names in grading/mastery prompts, repointable endpoint, plaintext LAN HTTP (Medium as configured; High if the endpoint ever leaves the school network, L3×S3)

**Evidence.** `_normalize_ollama_url` (`app.py:508-513`) accepts any http/https host with no allowlist; the admin save route (`app.py:3196-3220`) stores an arbitrary URL + admin-typed API key. Checked-in default is a LAN address over plaintext HTTP (`config.py:29`, `http://192.168.0.105:11434`). **What is sent:** student code verbatim in explain/grading prompts (`app.py:5829, 6295-6299, 6507-6517`); built-in grading prompts include **student names** — submissions are stamped `# Submitted by: <name>` (`assignment_workflow.py:336-347`), and `grading_code()` anonymizes only when passed `anonymous=True` (`assignment_workflow.py:213-218`), which the built-in grading prompts (`app.py:10963, 11023, 11147, 11195`) do not pass; **mastery feedback sends the whole class's names plus per-assignment/skill percentages** (`app.py:12897-12924`) although the names are not needed for the computation. Verified positives: notebook practice keeps identity local via a placeholder (`notebook_practice.py:356-362`); rubric generation sends no student data; the assistant-tutor prompt contains language/file/code but **no name or email** (verified by direct read, `app.py:6642-6680`); all generation funnels through one dispatcher — a single fix point.
**Scenario.** Today the data stays on the school LAN (to the owner's Ollama host) — but it crosses that LAN in cleartext (a LAN MITM can read schoolwork and *fabricate* "feedback"/grades the UI presents as the tutor's). If the endpoint is ever pointed at a hosted model — one admin form field — minors' names + code + class performance profiles leave to a processor with no DPA.
**Fix.** (1) Strip identity from prompts: pass `anonymous=True` in built-in grading (the stamp is metadata for humans; keep it in the stored submission, remove it from the model payload), and replace names with per-request pseudonyms (`Student 1…n`) in mastery feedback, mapping back server-side. (2) Allowlist the Ollama host: admin setting accepts a URL but the server warns/blocks if the host is not private/loopback unless an explicit `ALLOW_REMOTE_AI` flag is set; log endpoint changes. (3) Long-term, put Ollama behind a token (Ollama itself has no auth — front it with a local reverse proxy header check) or restrict its firewall to the app server only.
**Trade-offs.** Pseudonymized mastery feedback can read slightly less personally ("Student 3 improved…" is re-mapped to names server-side before display, so the teacher view is unchanged). Blocking remote endpoints removes the option of a hosted fallback model — deliberately, unless the flag is set with a DPA in place.
**Acceptance tests.** Prompt-capture test (mock dispatcher): grading and mastery prompts contain no student name/email; feedback rendered to the teacher still shows names; saving a public Ollama URL without the flag → rejected with a clear error.

### EAG-SEC-038 — "External" grading export is keyed by students' real emails (Medium code / High workflow, L3×S3)

**Evidence.** The external-grading package route (`app.py:12108ff`) is owner-only and — verified positives — excludes stored names, class/teacher identity, filenames, timestamps, and the generated submission header, with a strict atomic CSV import. But rows are keyed by the student's **real normalized email** and include full source code. `AGENTS.md`'s "excludes student names" framing understates this: the email *is* the identifier, and the workflow is designed to paste the package into an arbitrary external AI service outside any school agreement.
**Fix.** Key the export by an opaque per-assignment pseudonym (e.g., `S01…Snn` or an HMAC of the email under a per-export random key); keep the pseudonym↔email mapping in a separate file that never leaves the server, and make the import accept the pseudonym key. Update the `AGENTS.md` wording to match.
**Trade-offs.** The teacher loses the ability to eyeball-match exported rows to students in the external tool — the mapping file + import flow preserves the actual workflow (scores return keyed by pseudonym and are applied server-side).
**Acceptance tests.** Export fixture contains no substring matching any student email/name; import of the returned CSV applies scores to the correct students.

### EAG-SEC-039 — Public lesson-plan share link exposes the teacher's private notes; token never expires (High, L3×S4)

**Evidence.** Share tokens are strong mechanically (256-bit `secrets.token_urlsafe(32)`, constant-time compare, owner reset genuinely revokes — `lesson_plan_store.py:383, 392-418`). But `hydrate_plan` strips only `updated_by`, so the teacher's `notes_markdown` ("Additional notes") flows to `GET /api/lesson-plans/public/<token>` (`lesson_plan_features.py:195-200, 372-390`; `lesson_plan_store.py:372-390`), and the shared renderer has **no `publicPage` gate** on the notes block (`static/js/lesson-plan-renderer.js:289-298`). `ensure_public_token` returns the same token forever; no expiry field exists; public navigation reaches all past weeks. Verified positives: public payloads exclude student names, rosters, per-student deadlines, and accommodations (`agenda_assignments()` returns `{}` for token-only callers).
**Scenario.** A teacher's working notes — "extended time per IEP," custody or behavior details, sub plans with building specifics — become a permanent, forwardable bearer-link disclosure the moment the agenda link is shared with students/parents (its intended use).
**Fix.** Exclude `notes_markdown` from the public payload by default; add an explicit per-plan "share notes publicly" toggle (default off) for teachers who intentionally publish notes. Add optional token expiry (e.g., per-semester) with the existing reset as the manual path. Gate the renderer's notes block on the payload actually containing notes.
**Trade-offs.** Teachers who *were* (perhaps unknowingly) relying on public notes must flip the toggle once — communicate it in the UI ("Notes are private unless shared"). Nothing else changes; the embed/print flows keep their existing behavior (print tickets are teacher-side).
**Acceptance tests.** Public GET for a plan with notes → no `notes_markdown` key; toggle on → notes present; reset token → old token 404s (already true — pin it).

### EAG-SEC-040 — Print tickets reusable and unbound; share tokens travel in URLs/query strings (Medium, L3×S2)

**Evidence.** Print tickets are 256-bit, in-memory, 600 s, capped at 256 (positives) — but `get_print_export` uses `get`, not `pop` (not single-use), and binds only `class_id`+`week`, not teacher/session (`lesson_plan_features.py:131-150, 526-531, 641-650`). Share tokens travel in URL paths and in **query strings** for assets (`?share=`, `?print=`; `lesson_plan_resources.py:146, 160-162`), and the codebase's only log-redaction filter covers `/_tools/` capability URLs (`tool_gateway.py:253-258`) — nothing redacts lesson-plan tokens; the public page also lacks the embed page's `Referrer-Policy: no-referrer` (`app.py:405` vs `408`). Share tokens are additionally stored plaintext at rest in two files (`lesson_plan_store.py:386-389`) — unlike tool capabilities, which are stored as SHA-256 digests.
**Fix.** Make print tickets single-use (`pop` on first successful fetch) and bind them to the issuing teacher token's fingerprint. Move asset authorization from query tokens to short-lived path tickets where feasible; at minimum add `Referrer-Policy: no-referrer` to the public lesson page and extend the log-redaction filter to `/api/lesson-plans/public/` and `?share=`/`?print=` parameters. Store share tokens as SHA-256 digests at rest (compare by digest), matching the tool-capability pattern.
**Trade-offs.** Single-use print tickets break "reopen the print view to reprint" — mitigate by letting the teacher mint a fresh ticket per click (cheap) from the authenticated UI. Digest-at-rest means a forgotten token cannot be *displayed* again, only reset — the UI must shift from "copy your link" to "reset link" after first creation (show the full link once at creation/reset).
**Acceptance tests.** Second fetch with the same print ticket → 404; public page response carries `Referrer-Policy: no-referrer`; `catalog.json` contains no raw token substring.

### EAG-SEC-041 — Shared-photo route skips the ownership re-check (Medium, L2×S3)

**Evidence.** Notebook/agenda photo handling is otherwise a positive (re-encode + strip, quotas, UUID names, `private, no-store` previews, roster-membership authorization — `notebook_media.py:30-47, 120-186`). But the shared-photo route (`app.py:11790-11805`) skips the ownership re-check that its sibling route performs (`app.py:11828-11841`).
**Fix.** Apply the sibling route's ownership/class-access check verbatim to the shared-photo route (shared tabs copy bytes into the recipient's workspace by design — the check is about *whose* photo may be copied/served, not about blocking sharing).
**Trade-offs.** None expected; legitimate shares pass the same check the sibling route already enforces.
**Acceptance tests.** Cross-class/cross-owner photo access attempt via the shared route → 403; legitimate share → 200.

### EAG-SEC-042 — Tool launch sessions retain the raw bearer token; `?preview=1` capability quirk (Medium, L2×S3)

**Evidence.** External-tools launch sessions hold the raw EagleIDE bearer token server-side for up to 8 h (`external_tools.py:20-24, 397-408`) — never sent upstream and lost on restart (positives), but a memory disclosure yields live account tokens rather than scoped sub-credentials. Separately, `?preview=1` tool URLs act as unauthenticated view capabilities (`tool_gateway.py:226-228`). The gateway itself is the strongest code in the repo (see §10) — these are residuals at its edges.
**Fix.** Store a keyed HMAC of the token in the launch session and re-derive/validate against the live token maps on each use (the token maps are in-memory anyway, so validation-by-lookup is already the pattern); drop the raw value. For `?preview=1`, require an admin session or bind the preview capability to the admin who minted it with the same lease rules as launch capabilities.
**Trade-offs.** Slight added complexity in the session-validation path; preview links become non-shareable — they are an admin testing tool, so that is acceptable.
**Acceptance tests.** Memory/store inspection test: no raw token string in the launch-session store; preview URL without admin context → 401/404.

### EAG-SEC-043 — Lesson-plan link preview: validate-then-fetch TOCTOU (Low, L1×S3)

**Evidence.** Controls are genuinely good (teacher-only; scheme/port restrictions; resolves and rejects if *any* DNS answer is non-global; per-hop redirect re-validation; 4 s timeout; 128 KiB cap; only `<title>` kept — `lesson_plan_features.py:38-105`, `lesson_plan_store.py:119-134`). Residual: validation resolves DNS, then `urllib` re-resolves at connect — no pinning (unlike the tool gateway), so a rebinding domain can land on an internal 80/443 service. Exfiltration is limited to title + final URL + timing, and the attacker needs a teacher token.
**Fix.** Reuse the gateway's pinning approach: resolve once, connect to the checked numeric address with SNI/hostname preserved. Given the low residual risk, this is a "when touching the file" fix.
**Acceptance tests.** Existing link-preview tests pass; a rebinding fixture (DNS answers change between calls) → fetch refused.

### EAG-SEC-044 — Trace token and protected-file paths readable via `os.environ` (Low, L3×S1)

**Evidence.** `app.py:7854` sets `env["EAGLE_TRACE_TOKEN"]` (per-run `secrets.token_hex(24)`); the worker never scrubs `os.environ` (also `EAGLE_CONTROLLED_FILES`, containing absolute server paths of protected assignment files). A Step Mode student can read both, and could print a forged trace envelope — but only into their own session's playback (bounded by the 6 MB protocol cap and frame-shape validation), so impact is self-session UI spoofing plus minor path disclosure.
**Fix.** Pass the token via the worker control channel/fd instead of the environment, or scrub all `EAGLE_*` keys from `os.environ` in the worker immediately after bootstrap.
**Acceptance tests.** Step Mode run printing `os.environ` shows no `EAGLE_*` keys; tracing still works.

### EAG-SEC-045 — Sandbox residuals bundle (Low, L2×S2)

- **Post-spawn rlimit race (JS):** POSIX limits are applied via `prlimit` *after* `Popen` (`app.py:7284-7310`); the Python worker re-applies limits itself before executing student code (closing its window), the Node worker does not — JS limits depend on the parent winning a normally-comfortable ~ms race. Fix: have `js_worker.js` apply its own `setrlimit` equivalents at startup (or accept and document; bounded by wall-clock/output pumps).
- **Shared-UID `RLIMIT_NPROC`:** the per-UID task accounting (`app.py:7313-7348`) means a fork-bombing student consumes headroom shared with other runners and the server until the process-group SIGKILL lands (Windows is properly capped at 1 active process). The dedicated runner user from EAG-SEC-030 shrinks this blast radius.
- **`signal` module unlocked:** not in `SECURITY_LOCKED_MODULES` (`sandbox_policy.py:17`); students can ignore SIGTERM/SIGXCPU — worst case is burning their full allocation, since the parent escalates to process-group SIGKILL on an absolute deadline. Add `signal` to the locked set if no curriculum needs it.
- **`os.stat` metadata leak:** student Python can stat paths outside the workspace (existence/size/mtime); the audit hook governs `open`, and Landlock does not fully mediate getattr on ungranted paths. Minor filesystem-layout disclosure; accept or add a stat path check to the audit hook.
**Acceptance tests.** Existing sandbox suites green; a SIGTERM-ignoring script is still killed at the wall deadline.

### EAG-SEC-046 — Scripts-enabled preview with external internet allowed gets no CSP (Low, L2×S2)

**Evidence.** In the runtime view handler (`app.py` ~7160–7180), the CSP is set in the scripts-disabled branch and in the no-external-internet branch; when scripts are enabled **and** `html_runtime_allow_external_internet` is true, neither fires. The content remains confined to the isolated preview origin with no credentials, and the setting is operator-explicit — noted so the choice is conscious (and it interacts with EAG-SEC-031's main-origin issue, which is the real fix).
**Fix.** Always emit at least `Content-Security-Policy: sandbox allow-scripts` + `object-src 'none'` on runtime documents, even in the most permissive mode.
**Acceptance tests.** All four mode combinations assert a CSP header is present.

### EAG-SEC-047 — Supply chain: pins without hashes; unpinned pip upgrade; CI by major tag (Low, L1×S4)

**Evidence.** `requirements.txt`: 11 packages, all exact `==` pins (positive) — but no wheel hashes anywhere. `start.sh:186-187` runs `pip install --upgrade pip` (unpinned) then installs `--only-binary=:all:` without hash verification; the sha256-stamp mechanism (`start.sh:110-121, 165-196`) attests that what is installed matches the pins and loads from the venv — consistency, not provenance. CI (`.github/workflows/tests.yml`) has `permissions: contents: read` (positive) but references actions by major tag. No EOL components identified in the pinned set (Python ≥3.12, Node ≥18).
**Fix.** Generate and commit a hash-locked requirements file (`pip-compile --generate-hashes` or `pip download` + `--require-hashes`) for the production install path in `start.sh`; pin `pip` itself in the upgrade step; pin CI actions by commit SHA.
**Trade-offs.** Hash-locked installs make dependency updates a deliberate two-step (bump pin → regenerate hashes) and platform-specific wheel coverage must match the production LXC — generate them on the target platform.
**Acceptance tests.** Fresh venv install via `start.sh` setup-only mode succeeds with `--require-hashes`; tampering with one hash fails the install.

### EAG-SEC-048 — Default error pages and `Server` banner on LAN responses (Low, L4×S1)

**Evidence.** Only a 413 JSON handler exists (`app.py:390-392`); unhandled exceptions in feature modules render Werkzeug's default HTML error pages (no tracebacks — `debug=False`, `app.py:13315`). No code strips the `Server` header, so direct LAN responses carry the Werkzeug/Python version banner (Cloudflare masks it for tunnel traffic).
**Fix.** Add JSON 404/500 handlers matching the app's `{ok: false, error: …}` style, log the exception server-side with a request ID, and override/strip the `Server` header in the `after_request` hook.
**Acceptance tests.** Unknown route → JSON 404; forced exception in a test route → JSON 500 with request ID, no version strings in headers/body.

### EAG-SEC-049 — Workspace directory names reversibly encode emails (Low, L3×S1)

**Evidence.** `_sanitize_email_for_path` (`app.py:832-840`) produces `user_files/<sanitised-email>/` and `notebooks/<class>/<sanitised-email>.json` — trivially reversible to the student's email by anyone with a directory listing.

### EAG-SEC-050 — Socket.IO CORS relies on a library default (Low/Info, L1×S2)

**Evidence.** `cors_allowed_origins=None` (`app.py:377-385`) resolves to python-engineio's default — same-origin only, **not** wildcard — so the current posture is safe, but implicit. No Flask-CORS or manual `Access-Control-Allow-Origin` exists elsewhere in app code (the tool gateway's opaque-origin handling is separate and deliberate). REST auth rides in custom headers, so CORS is not load-bearing for the API.
**Fix.** Set `cors_allowed_origins` explicitly to the app's own origin(s). One line; do it when touching the file.

### EAG-SEC-051 — No CSRF tokens; posture rests on header-auth + SameSite (Low/Info, L1×S2)

**Evidence.** Grep for `csrf`: zero hits. API auth is via custom token headers (non-ambient — classic CSRF doesn't apply). The only cookie-authenticated endpoint, `POST /api/auth/restore`, is SameSite=Strict by cookie flag. No practical CSRF path exists today.
**Fix.** None now. Add an `AGENTS.md` rule: any future cookie-authenticated *mutating* endpoint must add a CSRF token or a custom-header requirement. Record the decision so a future contributor doesn't "fix" it blindly or break it unknowingly.

### EAG-SEC-052 — Authorization helpers trust the cached token record (Low, L1×S3)

**Evidence.** `_require_user` (`app.py:2274-2276`) returns the token-map record only; the plain-teacher path similarly trusts the cached record, while the CoTeacher branch *does* re-read the user record and check `enabled` (`app.py:1187-1201`). Every current disable/delete path purges tokens (so no live bypass was found) — the risk is structural: any future path, or a manual `users.json` edit, that disables an account without purging token maps leaves a zombie session until restart. The IDE-access gate does re-check membership/settings per request (`app.py:2294-2326`), limiting blast radius there.
**Fix.** In `_require_user`/`_require_teacher`, cheaply re-validate `enabled` (and role) against the current user record on each call — the users cache already exists; the CoTeacher branch is the pattern. Keep the token maps as the session store.
**Trade-offs.** One extra cached-dict lookup per request — negligible. Manual `users.json` edits then take effect without a restart, which is operationally nicer anyway.
**Acceptance tests.** Disable an account via direct record mutation (simulating a future path) → existing token immediately 401s; normal flows unaffected.

### EAG-SEC-053 — Tokens in JS-accessible `sessionStorage` (Medium, L2×S3)

**Evidence.** Tokens for all roles are stored as JSON in `sessionStorage` (`static/js/app-core.js:29, 175-186`). Any XSS in the app origin reads live tokens. Mitigations already present: `sessionStorage` (tab-scoped, cleared on tab close) rather than `localStorage`; tokens never appear in URLs (verified both sides); the long-lived device credential is HttpOnly and *not* exposed to JS.
**Fix.** No change to storage location is realistic for this header-token SPA design (the alternative — HttpOnly cookie sessions — is a larger auth redesign with its own CSRF costs, see EAG-SEC-051). The correct mitigations are the XSS defenses themselves: EAG-SEC-031 (runtime origin isolation), EAG-SEC-033 (CSP), EAG-SEC-034 (SRI), EAG-SEC-035 (fail-closed rendering), plus EAG-SEC-004's token TTL to bound what a stolen token is worth. This finding closes when those land; it is tracked separately so the dependency is explicit.
**Acceptance tests.** N/A (dependency tracking).

**External-tools gateway (strongest code in the repo).** Real DNS pinning with no TOCTOU (`tool_gateway.py:70-99, 115-127`): every answer must be private *and* admin-approved *and* not denied *and* not a self address; loopback/link-local/multicast/unspecified and both cloud metadata addresses (`169.254.169.254` via link-local, `fd00:ec2::254` by literal) rejected; connection made to the checked numeric IP with TLS SNI/hostname preserved. Runtime re-resolution requires admin re-approval. Redirect containment to the tool's base path. Capability URLs are `token_urlsafe(32)`, stored only as SHA-256 digests, 90 s lease / 8 h hard cap, entitlement re-validated on *every* proxied request. Cookies/`Authorization`/forwarding headers are never sent upstream; upstream `Set-Cookie`/401/407 aborts. Proxied content gets a sandbox CSP (no `allow-same-origin`) on top of upstream policy. Capability tokens are redacted from logs. Catalog writes are atomic with fsync.

**Python sandbox.** Landlock grants: workspace full access + an enumerated read-only list (code file, worker, Python prefixes, lib dirs, fonts) — the repo/data directory is *not* granted; `PR_SET_NO_NEW_PRIVS` before `restrict_self`; native modules fail closed below Landlock ABI 3. Audit hook blocks `socket.*`, `ctypes.dlopen`, `os.exec*/fork/spawn/system`, `subprocess.Popen`; `open` and `sqlite3.connect` path-checked (file: URIs and extension loading blocked); dangerous modules defanged post-bootstrap; 10 MB write budget / 20 new files; rlimits (750 MB AS, 8 s CPU, NOFILE 64, CORE 0); tracebacks redact server paths. Runner environment is a strict allowlist — server secrets are not inherited; HOME/TEMP point into the run dir. Per-run UUID sandbox dirs created `exist_ok=False`, cleaned via root-checked `rmtree`, stale sweep at startup; output capped 200 KB / 5,000 lines; workspace quota re-checked every 2 s during runs.

**Step Mode.** Same worker and boundaries; `trace_support.py` never calls `repr` on student objects (type-switch `safe_value`), so a hostile `__repr__` cannot execute during tracing; hard bounds on steps/variables/value sizes; 6 MB wire cap with frame-shape validation.

**JavaScript worker hygiene.** `codeGeneration: {strings: false, wasm: false}`, frozen host bridge and console, dynamic `import()` denied with a realm Error, host paths redacted, no `fetch`/`require`/`Buffer` exposed, heap + address-space caps, dedicated regression tests for constructor escapes. (The gap is the missing OS backstop — EAG-SEC-030 — not the vm hygiene.)

**Run admission.** One active *or queued* run per account across tabs/sockets; guest per-IP caps on active (2) and queued (4) runs; start-rate window keyed by guest-IP identity so socket reconnects don't reset limits; global capacity CPU-derived with reserved-memory accounting against total RAM minus ≥20 %/1 GB headroom; pressure gate refuses launches at low disk/memory; queued promotion re-derives authorization.

**Auth & sessions.** bcrypt (cost 12) for all user passwords; legacy auto-upgrade on login; device-cookie fingerprint `sha256(role\0email\0password_hash)` so any password change invalidates all device cookies; cookie is HttpOnly + SameSite=Strict + Fernet-encrypted with strict restore validation (version, role, token format, expiry, fingerprint, `enabled`); admin login uses one generic error + `compare_digest` on both fields; password resets revoke the target's tokens; self-service changes verify the current password and revoke other sessions; disable/delete purge tokens; `/api/config` GET and save strip admin credential fields (the API cannot overwrite admin credentials); tokens are 128-bit CSPRNG, header-carried, never in URLs, never in `localStorage`, never logged.

**Authorization.** Admin routes uniformly gated by `_require_admin`; CoTeacher routes re-read the user record and re-check `enabled` + membership per request; class ownership checks are consistent; IDs are uuid4 (no sequential IDOR); Socket.IO privileged events authenticate per event, room joins re-verify membership/ownership against fresh records, and `run_code` validates tokens + IDE access + guest caps. (Two early automated-scan suspicions — rubric generation and submission-file routes — were manually verified as properly ownership-checked; they are *not* findings.)

**Data handling.** Notebook and agenda photos are re-encoded with EXIF stripped (test-pinned); provenance sidecars store ranges + hashes only, never content, and are omitted from student payloads; clipboard policy transmits and stores nothing (grep-verified — the probe is source-free by construction); CSV grade/notebook exports contain `student_id` + score only (verified by direct read — an early suspicion that they contained names/emails/response text was checked and **withdrawn**); the external grading export excludes names/class/teacher/filenames/timestamps; the assistant-tutor prompt contains no student name/email (verified by direct read); lesson-plan public payloads exclude rosters/accommodations/per-student deadlines; link previews are SSRF-guarded (non-global rejection, redirect re-validation, size/time caps); wiki backup download tickets are single-use, 300 s, admin-created; backup restore validates manifests, checksums, and paths and rolls back on failure; classroom events and sign-in events have real retention bounds (90 d); Trash mechanics (protected root, provenance-aware purge, immediate permanent delete) are sound.
