External Tools setup

Register independently deployed applications beneath the existing EagleIDE hostname. The catalog starts empty and the gateway starts disabled. EagleIDE does not install or modify applications, manage Proxmox, provide application SSO, or save their projects.

The admin manager separates Applications, Network & access, and a Compatibility guide with common failure symptoms. Tool sessions use the full workspace beneath a compact site banner; Info shows status and saving help. Reload restarts the app after a confirmation. Routine access checks and viewport changes retain the same document and its unsaved work. A tab suspended beyond its lease can expire and must reopen.

Before enabling

  • Use an unprivileged private application container with its own data and resource quotas. Do not mount host filesystems or management/Docker sockets.
  • Allow only the required EagleIDE-to-application port. Block application-initiated access to EagleIDE, management and unrelated LAN services; restrict unnecessary egress. Configure these boundaries in your infrastructure.
  • The existing Cloudflare hostname must already forward all paths to EagleIDE’s existing listener. Verify that protected /_tools/ and tool API responses are not cached by edge rules. Live tunnel/cache settings are not verified by EagleIDE.
  • Use current supported browsers. Applications must support relative URLs or a documented prefix/base-URL setting, embedding, and the restricted browser profile below.

Administrator workflow

  1. Open the account menu → Settings → External Tools → External Tools.
  2. Choose Network & access. Enter a narrow private application subnet in Allowed application networks. Enter management networks and EagleIDE addresses in Denied CIDRs; host entries use /32 (IPv4) or /128 (IPv6). Enable External Tools and save policy. Every policy change disables tools and requires retesting.
  3. Add a name, homepage label, full private backend URL such as http://private-host:8080/optional-base/, and a single public launch path such as /design/. Reserved or duplicate paths are rejected. In Applications, start with both permissions off. “Send data to the app server” enables POST/PUT/PATCH/DELETE for server saves, API actions or uploads (1 MiB request limit). “Submit HTML forms” enables traditional form submission; POST forms also require server data permission. Scripts, styles, images, modules, WASM and browser-only editing/downloads do not require either permission. These options never enable cookies or login.
  4. Save the disabled tool, then Test connection. DNS answers must be private, allowed, not denied, and not an EagleIDE address. All answers are checked. Runtime connects to the validated numerical address while preserving HTTPS certificate/hostname verification; changed DNS answers require retesting.
  5. Open Private preview. Test rendering, modules, WASM, fonts, API requests, imports, downloads, navigation and intended saving behavior. A reachable server or loaded document does not establish compatibility.
  6. Close the preview, return to External Tools, and confirm compatibility to enable. The confirmation requires a recently delivered preview of that configuration. A broken or incompatible application must remain disabled; there is no permissive fallback.

Saving any tool edit disables it and invalidates prior instances/verification. Disable/delete revokes gateway delivery; deleting a registration does not delete the separately deployed application or its data. The private address and diagnostics are administrator-only.

Teacher and student workflow

Class owners open Dashboard → Classes → External Tools, select globally enabled tools, and save access. CoTeachers cannot change grants. Signed-in students see homepage buttons for the union of grants across their current enrolled classes, regardless of the selected homepage class. Teachers can open every globally enabled, verified tool without class grants or class ownership. CoTeachers retain student tool-access rules. Guests have no access.

Removing the last grant or membership, disabling an account/tool, or logging out blocks further gateway requests. Existing downloaded/running browser code cannot be recalled. The hosted workspace periodically revalidates and disposes revoked instances.

Integrity-protected applications such as SolidCraft

Inside the opaque sandbox, stylesheets and classic scripts with Subresource Integrity need anonymous CORS requests. The gateway adds crossorigin="anonymous" to integrity-bearing link/script start tags that lack it, keeping their URLs, hash values and source code intact. Browser integrity checks and upstream CSP still apply. This fixes SolidCraft’s stylesheet being blocked after the splash screen. The web release is self-contained and does not need forms or server-write permission for ordinary CAD editing and downloads. Browser project storage and offline installation remain unavailable: use the app’s download/export controls to retain work.

Restricted profile and limits

Applications run in an opaque-origin sandbox without allow-same-origin. The same sandbox is also enforced by response headers on directly opened application documents. Do not relax it to make an application fit.
Supported after verificationUnsupported / not promised
Relative/prefix-hosted static HTML, JS modules, CSS, WASM, fonts and images; bounded compatible HTTP APIs; user-initiated downloads; optional formsCookies/login challenges, shared-origin parent access, localStorage/OPFS assumptions, service workers/offline installation, popups/nested frames, root-only assets, unavoidable off-host dependencies, WebSockets/application Socket.IO/SSE, EagleIDE SSO and seamless project saving

Original application bytes are streamed without broad HTML/JavaScript rewriting. Upstream restrictive CSP/frame headers remain in effect. The profile restricts scripts and connections to that instance’s gateway prefix; the inline script/style and WASM permissions do not grant access to EagleIDE’s origin. Narrow Origin: null CORS applies only to already authorized capability resources and allows no ambient credentials. Origin alone never authorizes a request.

Native imports/downloads must be tested. Browser storage may fail under this profile; ordinary proxying does not provide per-student project isolation. There is no blanket site-data clearing, which could erase notebook recovery. Do not register applications that expose another student’s native data or require unsupported storage/login behavior.

Limits: 32 tools, 256 in-memory instances, two active instances per EagleIDE session, 16 upstream connections globally and four per session, 1 MiB write bodies, 256 MiB streamed responses, three-second connect timeout, 15-second upstream read-idle and five-second client write-idle timeouts, a 15-second upload deadline and a 180-second response budget. Asset bursts wait up to 15 seconds in a bounded queue (64 waiting globally, 12 per session) while preserving the 16/four active connection limits. Access is checked again after waiting. HTML documents are buffered up to 2 MiB (including bounded gzip/deflate decoding); data, JS and WASM remain streamed. Admission precedes body reads. Writes require the supported threaded Werkzeug listener or an already buffered test input; other WSGI upload streams fail closed. Conditional and Range request headers are not forwarded; resources use full bounded responses. Upstream cookies, EagleIDE tokens, browser cookies, Authorization and client forwarding headers are never forwarded.

Capability URLs are credentials scoped to one tool instance, not account tokens. They expire after 90 seconds without a parent renewal and after eight hours in all cases, and require the originating EagleIDE session/current entitlement. Do not share them. EagleIDE redacts them from its Werkzeug access logs and uses no-referrer/private no-store delivery; independently configured edge/network logging must also protect these paths.

Independent updates and rollback

Pin each application release/image digest. Test an independently deployed candidate with a disabled registration/private preview. Schedule maintenance, ask users to save/download, close active instances, update the backend, retest and reapprove. Do not replace assets beneath active sessions: mixed builds and hot swaps are not supported. Keep the prior image, configuration, and pre-upgrade application-data/project-format backups for rollback.

Runtime data and verification

The atomic registry and class grants live in tool_data/catalog.json; capabilities stay in memory and expire on server restart. Back up the catalog as private configuration. EAGLEIDE_TOOL_DATA_DIR overrides its directory for isolated tests/deployment. Invalid catalogs fail closed.

The automated checks use a generic local fixture only. Run python -m unittest discover -s tests -p test_external_tools.py -v and node --test tests/external_tools_ui.test.js. Optional real-browser checks use python tests/external_tools_browser_fixture.py, then a separate shell with Playwright available, EAGLE_TOOL_TEST_URL set to its printed localhost URL, and EAGLE_TOOL_SCREENSHOT_DIR set to an existing output directory: node tests/external_tools_browser_checks.js. No production accounts or application packages are used.
