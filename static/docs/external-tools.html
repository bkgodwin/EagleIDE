External Tools setup

Register independently deployed applications beneath the existing EagleIDE hostname. The catalog starts empty and the gateway starts disabled. EagleIDE does not install or modify applications, manage Proxmox, or provide arbitrary application SSO. Optional account cloud storage preserves data written through the localStorage compatibility layer.

The admin manager separates Applications, Network & access, User storage, and a Compatibility guide with common failure symptoms. Tool sessions use the full workspace beneath a compact site banner; Info shows status and saving help. Reload restarts the app after a confirmation. Routine access checks and viewport changes retain the same document and its unsaved work. A tab suspended beyond its lease can expire and must reopen.

Before enabling

  • Use an unprivileged private application container with its own data and resource quotas. Do not mount host filesystems or management/Docker sockets.
  • Allow only the required EagleIDE-to-application port. Block application-initiated access to EagleIDE, management and unrelated LAN services; restrict unnecessary egress. Configure these boundaries in your infrastructure.
  • The existing Cloudflare hostname must already forward all paths to EagleIDE’s existing listener. Verify that protected /_tools/ and tool API responses are not cached by edge rules. Live tunnel/cache settings are not verified by EagleIDE.
  • Use current supported browsers. Applications must support relative URLs or a documented prefix/base-URL setting, embedding, and the restricted browser profile below.

Administrator workflow

  1. Open the account menu → Settings → External Tools → External Tools.
  2. Choose Network & access. Enter a narrow private application subnet in Allowed application networks. Enter management networks and EagleIDE addresses in Denied CIDRs; host entries use /32 (IPv4) or /128 (IPv6). Enable External Tools and save policy. Every policy change disables tools and requires retesting.
  3. Add a name, homepage label, full private backend URL such as http://private-host:8080/optional-base/, and a single public launch path such as /design/. Reserved or duplicate paths are rejected. In Applications, choose the permissions needed by the app. “Send data to the app server” enables POST/PUT/PATCH/DELETE for server saves, API actions or uploads (1 MiB default, configurable up to 16 MiB per request including multipart overhead). “Submit HTML forms” enables traditional form submission; POST forms also require server data permission. Scripts, styles, images, modules, WASM and browser-only editing/downloads do not require either permission. These options never enable cookies or login.
  4. Save the disabled tool, then Test connection. DNS answers must be private, allowed, not denied, and not an EagleIDE address. All answers are checked. Runtime connects to the validated numerical address while preserving HTTPS certificate/hostname verification; changed DNS answers require retesting.
  5. Open Private preview. Test rendering, modules, WASM, fonts, API requests, imports, downloads, navigation and intended saving behavior. A reachable server or loaded document does not establish compatibility.
  6. Close the preview, return to External Tools, and confirm compatibility to enable. The confirmation requires a recently delivered preview of that configuration. A broken or incompatible application must remain disabled; there is no permissive fallback.

Saving any tool edit disables it and invalidates prior instances/verification. Disable/delete revokes gateway delivery; deleting a registration does not delete the separately deployed application or its data. The private address and diagnostics are administrator-only.

Teacher and student workflow

Class owners open Dashboard → Classes → External Tools, select globally enabled tools, and save access. CoTeachers cannot change grants. Signed-in students see homepage buttons for the union of grants across their current enrolled classes, regardless of the selected homepage class. Teachers can open every globally enabled, verified tool without class grants or class ownership. CoTeachers retain student tool-access rules. Guests have no access.

Removing the last grant or membership, disabling an account/tool, or logging out blocks further gateway requests. Existing downloaded/running browser code cannot be recalled. The hosted workspace periodically revalidates and disposes revoked instances.

Integrity-protected applications such as SolidCraft

Inside the opaque sandbox, stylesheets and classic scripts with Subresource Integrity need anonymous CORS requests. The gateway adds crossorigin="anonymous" to integrity-bearing link/script start tags that lack it, keeping their URLs, hash values and source code intact. Browser integrity checks and upstream CSP still apply. This fixes SolidCraft’s stylesheet being blocked after the splash screen. The web release is self-contained and does not need forms or server-write permission for ordinary CAD editing and downloads. Enable Account cloud storage to use SolidCraft’s localStorage fallback for its named designs and autosave. The gateway disables unavailable File System Access pickers before app startup, allowing its existing ordinary file-input fallback. Use the app’s Files menu → Open from computer / Insert from computer for STEP or other supported files, and Download open design or export to keep an independent copy. Its OPFS warning is expected; localStorage saves are synchronized to EagleIDE. Offline installation remains unavailable.

Restricted profile and limits

Applications run in an opaque-origin sandbox without allow-same-origin. The same sandbox is also enforced by response headers on directly opened application documents. Do not relax it to make an application fit.
Supported after verificationUnsupported / not promised
Relative/prefix-hosted static HTML, JS modules, CSS, WASM, fonts and images; bounded compatible HTTP APIs; local file selection, downloads; optional forms, sandboxed popups, native prompts/dialogs and account localStorageCookies/login challenges, shared-origin parent access, native IndexedDB/OPFS, service workers/offline installation, nested frames, root-only assets, unavoidable off-host dependencies, WebSockets/application Socket.IO/SSE, automatic login to unrelated apps, live RAM sessions or generic whole-app synchronization

Binary assets and upstream scripts are streamed intact. A blocking compatibility bootstrap is inserted before application startup in HTML documents; it exposes only that account/tool storage and file-picker fallbacks. Upstream restrictive CSP/frame headers remain in effect. The profile restricts scripts and connections to that instance’s gateway prefix; the inline script/style and WASM permissions do not grant access to EagleIDE’s origin. Narrow Origin: null CORS applies only to already authorized capability resources and allows no ambient credentials. Origin alone never authorizes a request.

Native imports/downloads and cloud saves must be tested with real projects. The optional localStorage layer provides isolated account/tool data; it does not synchronize IndexedDB, OPFS, cookies or arbitrary backend accounts. Native server-side data still needs its own application authorization. There is no blanket site-data clearing, which could erase notebook recovery. Do not register applications that expose another student’s native data or require unsupported storage/login behavior.

Limits: 32 tools, 256 in-memory instances, two active instances per EagleIDE session, 16 upstream connections globally and four per session, 1–16 MiB configured write bodies (default 1 MiB), 256 MiB streamed responses, three-second connect timeout, 15-second upstream read-idle and five-second client write-idle timeouts, a 15-second upload deadline and a 180-second response budget. Asset bursts wait up to 15 seconds in a bounded queue (64 waiting globally, 12 per session) while preserving the 16/four active connection limits. Access is checked again after waiting. HTML documents are buffered up to 2 MiB (including bounded gzip/deflate decoding); data, JS and WASM remain streamed. Admission precedes body reads. Writes require the supported threaded Werkzeug listener or an already buffered test input; other WSGI upload streams fail closed. Conditional and Range request headers are not forwarded; resources use full bounded responses. Upstream cookies, EagleIDE tokens, browser cookies, Authorization and client forwarding headers are never forwarded.

Capability URLs are credentials scoped to one tool instance, not account tokens. They expire after 90 seconds without a parent renewal and after eight hours in all cases, and require the originating EagleIDE session/current entitlement. Do not share them. EagleIDE redacts them from its Werkzeug access logs and uses no-referrer/private no-store delivery; independently configured edge/network logging must also protect these paths.

Account cloud storage and safe saving

New accounts have 64 MiB across tools. In External Tools → User storage, an administrator can load an email and enable/disable storage or set 1–1024 MiB. Existing tool registrations keep cloud storage, popups and dialogs off until edited, previewed and reapproved; new-tool forms select those options explicitly. Stored profiles use an internal account UUID, so signing in on another computer loads that account’s saved tool data and recreating a deleted email cannot inherit it. Account deletion removes its stored profiles. The administrator has its own profile.

All account dashboards and the account menu provide External tool storage: usage, per-tool backup/clear and Clear external tool storage. Clearing deletes cloud data across devices and invalidates pending old saves; download designs first. Disabling/lowering a quota retains existing data for backup or clearing. Other EagleIDE data, browser preferences and notebook recovery are unaffected. Backups are JSON key/value recovery data, not a replacement for the app’s native project exports.

Apps see synchronous localStorage in the opaque frame. Only changes are uploaded, in 512 KiB chunks, and become visible atomically after revision-checked commit. One value is limited to 32 MiB UTF-8, a profile/batch to 64 MiB, and a profile to 2048 keys (512 bytes/key). Encoded binary data counts at its encoded size (SolidCraft uses hexadecimal). A 2 GiB server budget, 32 pending uploads, five-minute upload expiry, disk-space checks and existing request admission bound resource use. At most two full snapshots/exports are materialized at once, with five-second client write-idle timeouts; permits release on response exhaustion or close. These are compatibility storage limits, not browser-native storage quotas.

The banner says Storage synced only for data already written by the app. It cannot know about edits still in app memory; SolidCraft autosaves periodically, so use Save/Save As and wait for sync before closing. Offline/quota/conflict errors remain visible with Retry save and Download storage backup in Info. Keep the tab open until saving finishes. Concurrent edits on another device never silently overwrite a newer profile: export unsaved work, then reopen. Unsynced changes cannot follow a sign-out or server-side access revocation. Fresh EagleIDE authentication is required on each device; this does not sign users into unrelated app accounts.

Popups and prompts are optional per tool. Popups inherit the sandbox; no allow-popups-to-escape-sandbox or allow-same-origin is granted. Script-opened windows are closed on normal tool departure. Browser popup policies and user gestures still apply. Prompts can interrupt work, so enable them only for trusted registered applications.

Independent updates and rollback

Pin each application release/image digest. Test an independently deployed candidate with a disabled registration/private preview. Schedule maintenance, ask users to save/download, close active instances, update the backend, retest and reapprove. Do not replace assets beneath active sessions: mixed builds and hot swaps are not supported. Keep the prior image, configuration, and pre-upgrade application-data/project-format backups for rollback.

Runtime data and verification

The atomic registry and class grants live in tool_data/catalog.json; account cloud data lives in tool_data/storage/catalog.sqlite3. Upload spools in that folder are temporary. Capabilities stay in memory and expire on server restart. Back up the catalog, storage database and users.json together as private data, with the server stopped or using SQLite’s backup API. EAGLEIDE_TOOL_DATA_DIR overrides its directory for isolated tests/deployment. Invalid catalogs fail closed.

The automated checks use a generic local fixture only. Run python -m unittest discover -s tests -p test_external_tools.py -v and node --test tests/external_tools_ui.test.js. Optional real-browser checks use python tests/external_tools_browser_fixture.py, then a separate shell with Playwright available, EAGLE_TOOL_TEST_URL set to its printed localhost URL, and EAGLE_TOOL_SCREENSHOT_DIR set to an existing output directory: node tests/external_tools_browser_checks.js. No production accounts or application packages are used.
